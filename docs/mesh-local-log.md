# 승인 장치 연결과 로컬 톡 원본

> 이전 PC 톡 저장 구조의 기록입니다. 2026-11-17의 [새 개발 방향](development-direction.md)에 따라 팀원 간 톡은 제거 대상입니다. 이 문서를 새 채팅 기능의 개발 지시로 사용하지 않으며, 기존 사용자 자료는 별도로 보존·이전 여부를 정합니다.

2026년 11월 16일, 장기 장치 신원을 TLS 연결 확인에 적용하고 톡의 로컬 원본·발신 대기함을 구현했다. 외부 조정 서비스나 추가 연결 프로그램을 사용하지 않는다. 이번 단계의 자동 검증에는 두 번째 PC가 필요하지 않다.

## 1. 현재 동작

| 기능 | 구현 범위 |
|---|---|
| 승인 장치 연결 | 관리자 승인을 받은 장치의 서명과 실제 상호 TLS 연결을 함께 확인 |
| 로컬 톡 | 승인된 내 장치가 팀별 순번·이전 해시·본문 해시·수신 장치 목록에 서명하고 저장 |
| 본문 보관 | Windows 사용자 계정의 DPAPI로 보호. 평문 저장 대체 경로 없음 |
| 발신 대기함 | 원본·마지막 순번과 같은 SQLite 트랜잭션으로 기록 |
| 재시도 | 같은 요청 ID와 같은 본문이면 같은 원본 ID 반환. 같은 요청의 내용 변경은 거부 |
| 화면 | 로컬 저장·발신 대기 수와 최근 50개 원본 표시. 팀별 입력 보존과 오류 후 재시도 |

초기 로컬 저장 기반에 이어 [암호화된 준비 톡 교환과 상대 저장 확인](mesh-record-exchange.md)을 추가했다. 연결 확인만 켜면 인증 신호만 교환하며, 별도로 양쪽이 기록 교환에 동의한 연결에서 준비 톡을 교환할 수 있다. 자동 호스트 전환은 후속 구현이다. 연결 확인 성공을 톡 전달 완료로 처리하지 않는다.

기존 팀 톡·Firebase·고정 PC 서버의 원본이나 대기함도 이번 준비 기능으로 자동 이전하지 않는다. 기존 개인 상담·로그인 토큰·Google 연동을 복제하지 않는다.

## 2. 준비 화면

일반 앱의 **설정 → PC 팀 장치 등록 준비 → 내 장치와 관리자 승인 정보**에서 PC 팀을 선택하고 **승인 장치 연결과 암호화된 준비 톡 교환**을 펼친다. 먼저 [장치 등록과 관리자 승인](mesh-identity.md)을 완료해야 새 톡을 저장하거나 승인 연결을 열 수 있다.

### 로컬 저장

`이 PC에 보관할 톡`에 내용을 입력하고 `이 PC에 저장`을 누른다. 디스크 커밋이 성공한 뒤 원본과 발신 대기 수를 표시한다. 로컬 저장에는 네트워크를 열 필요가 없으며 앱 재실행 후에도 원본을 읽는다. 후속 교환 구현에서는 상대 저장 확인·승인 이력 변경·이전 로컬 전용 여부에 따라 상태를 구분한다. 초기 v2에서 작성한 로컬 확인용 본문은 자동 전송하지 않는다.

저장 오류가 나면 입력을 지우지 않는다. 같은 내용을 재시도할 때 기존 요청 ID를 사용해, 커밋은 되었으나 응답을 못 받은 상황의 중복 저장을 막는다. 입력을 바꾸면 다른 요청으로 취급한다. 팀을 바꾸면 화면이 열린 동안 팀별 작성 내용을 보존한다. 아직 저장하지 않은 입력과 재시도용 화면 상태를 앱 종료 후 복원하는 기능은 없다. 이미 저장된 톡은 DB에서 복원한다.

장치 등록이 해제되면 과거 원본은 읽을 수 있지만 새 저장은 거부한다. 새 장치가 기존 장치의 순번이나 개인키를 이어받지 않는다.

### 승인 장치 연결

1. 양쪽 PC에 같은 최신 관리자 승인 이력을 등록한다.
2. 각각 실제 LAN 주소를 고르고 수신 동의를 체크한 뒤 연결 확인을 시작한다.
3. `상대에게 전달할 서명된 연결 정보`를 서로 복사해 등록한다.
4. 등록된 상대의 `연결 확인`을 누른다. 양쪽에서 확인할 수 있다.
5. `중지`를 누르거나 최대 15분이 지나면 런타임과 소켓을 정리한다.

이 흐름은 기능을 수동 확인할 때의 안내이며, 다음 개발을 위해 사용자가 지금 수행해야 하는 절차는 아니다. 자동 테스트는 한 PC에서 서로 다른 저장소·키·TCP listener를 사용하는 장치를 만들어 같은 인증 경로를 실행한다.

연결을 시작한 뒤 다른 PC 팀을 선택해도 실행 중인 연결의 팀은 유지한다. 상태에 표시된 팀 ID로 구분하고, 다른 팀으로 연결하려면 중지 후 다시 시작한다. 관리자 승인 이력이 달라지면 최신 자료를 양쪽에 등록하고 다시 시작한다. 승인 이력의 자동 전달은 아직 제공하지 않으며, 승인된 장치의 [LAN 자동 발견·재연결](mesh-automatic-connection.md)은 별도 동의 모드로 추가했다.

기존 `PC 연결 실험`과 별도 `Sai-Connection-Test.exe`는 임시 카드만 사용하는 단계 0 진단으로 유지한다. 새 키나 로컬 톡을 초기화하지 않는다. 승인 연결은 일반 앱의 별도 명령과 런타임을 사용한다.

## 3. 연결 인증

연결마다 새 TLS 인증서와 실험 ID를 만든다. 장치 개인키는 인증서·실험 ID·사설 IPv4 주소와 포트의 정해진 직렬화 해시에 서명한다. 증명에는 팀 ID, 장치 ID, 승인 이력 순번·마지막 해시를 포함한다. 서명 용도는 `sai-mesh/session/1`, 카드 해시 용도는 `sai-mesh/tls-card/1`이다.

상대 등록 시 관리자 승인 이력, 두 장치의 현재 승인 상태와 카드 서명을 검사한다. 실제 접속에서도 TLS 1.3의 인증서 체인·소유 증명과 등록 인증서의 정확한 일치를 확인한다. 인증 신호의 실험 ID와 새 난수를 대조하고, 응답 전후 현재 승인 이력으로 다시 검사한다.

승인 확인은 DB의 일관된 읽기 스냅샷을 기준으로 한다. 등록 뒤 해제 정보를 받은 장치는 새 확인 요청을 거부한다. 해제 사실을 아직 받지 못한 다른 PC에 즉시 전파되는 것은 아니다. 권한 변경과 진행 중인 모든 패킷을 전역적으로 원자화한다고 주장하지 않는다.

연결 확인의 ALPN은 `sai-approved-probe/1`이며, 교환에 별도로 동의하면 `sai-mesh-transfer/1`도 허용한다. 기존 임시 실험의 `sai-probe/1`로 내려가 인증을 생략하지 않는다. TLS 세션 재개 티켓을 발급하지 않는다. 중지·만료·인증 전 작업 수 제한은 기존 진단 런타임과 공유한다. 수동 모드는 서명된 주소를 사용하고, 자동 모드는 mDNS에 불투명 표식만 광고한 뒤 새 도전·암호화·장치 서명을 거쳐 주소를 확인한다. 포트 자동 개방·방화벽 변경·외부 중계는 수행하지 않는다.

## 4. 원본과 대기함

초기 로컬 기반은 같은 `mesh/identity.sqlite3`에 스키마 v2의 아래 테이블을 추가했다. 현재 교환 구현은 이를 보존하고 v3로 갱신한다. 상세한 추가 테이블과 이전 기록의 보류 정책은 [기록 교환 문서](mesh-record-exchange.md)를 따른다. 해당 스키마를 모르는 이전 앱은 열기를 거부하므로 DB 버전을 임의로 되돌리지 않는다.

| 테이블 | 내용 |
|---|---|
| `mesh_local_events` | 팀·작성 장치·순번·원본 ID·요청 ID·서명된 헤더·보호된 본문 |
| `mesh_local_heads` | 팀·작성 장치별 마지막 순번과 원본 ID |
| `mesh_local_outbox` | 해당 로컬 원본의 발신 대기 참조 |

헤더는 버전, 팀, 작성 장치, 연속 순번, 이전 원본 해시, 요청 ID, 작성 당시 승인 이력 순번·해시, 승인된 수신 장치 목록, 본문 해시를 포함한다. 자기 장치도 수신 목록에 포함한다. 서명 용도는 `sai-mesh/local-event/1`이며, 교환할 때 원본을 유지한 채 수신자별 암호문과 작성자 서명을 가진 전송 봉투로 감싼다.

본문 해시는 DPAPI 봉투 안에만 보관한 난수 salt와 본문으로 계산한다. 봉투에는 버전과 원본 ID도 넣어, 암호문을 다른 행으로 바꿔 끼운 경우를 탐지한다. 팀·장치·순번·수신 목록·원본 크기 같은 메타데이터까지 암호화하는 것은 아니다. 같은 Windows 사용자 권한을 가진 악성 프로그램이나 운영체제 장악을 방어한다고 보장하지 않는다.

추가 저장 전에 기존 헤더들의 서명·승인 이력·연속 순번·부모 해시와 마지막 저장 기록·대기함의 일치를 검사한다. 화면에 표시하거나 재시도하는 본문은 보호 해제 후 원본 ID·해시도 검사한다. 원본 끝부분이나 대기함이 없어진 경우 순번을 자동 초기화하거나 완료로 표시하지 않는다. 디스크 오류로 일부 SQL이 실패하면 원본·순번·대기함을 모두 롤백한다.

DB 전체를 과거 백업으로 되돌리거나 관련 테이블을 모두 조작한 경우까지 로컬 기록만으로 탐지하지 못한다. 향후 실제 이벤트 전송 전 피어의 저장 경계 대조와 백업 복원 정책이 필요하다. 현재는 기록 삭제·대기함 비우기·DB 내보내기·상대 확인 없이 완료 처리하는 명령을 제공하지 않는다.

준비 버전의 한도는 본문 UTF-8 32 KiB, 팀·작성 장치별 원본 1,024개다. 화면의 글자 수 제한과 별개로 네이티브 코드가 바이트 크기를 확인한다. 한도에 도달하면 원본을 임의로 지우지 않고 저장을 거부한다. 이 원본들을 향후 메시지 프로토콜로 이전하는 버전 정책은 별도로 구현한다.

## 5. 검증

```powershell
cargo test --locked --workspace --target x86_64-pc-windows-msvc --features sai/connection-test
cargo check --locked -p sai-ui --target wasm32-unknown-unknown
cargo run --locked -p xtask --target x86_64-pc-windows-msvc -- ui
```

새 테스트 14개는 실제 Windows DPAPI·SQLite·상호 TLS를 사용한다. 승인 장치 간 양방향 연결, 인증서·주소·증명 바꿔치기, 등록 후 해제, 승인 이력 갱신, 미승인 장치와 이전 ALPN 거부를 확인한다. 로컬 원본·대기함 재열기, 중복 요청, 동시 저장, 저장 중 오류와 롤백, 본문 보호·행 바꿔치기, 꼬리 기록 유실, 해제 뒤 쓰기 거부, 잘못된 입력과 v1→v2 보존도 검증한다.

초기 로컬 기반 확인 당시 전체 워크스페이스 테스트 103개가 통과했다. 실제 LAN 지정 테스트 1개와 외부 Firebase 테스트 3개는 일반 실행에서 제외했다. WebAssembly 검사와 릴리스 화면 빌드도 통과했고, 화면 ID·로컬 문서 링크·진단 앱의 명령 분리를 확인했다. 후속 검증 상태는 [기록 교환 문서](mesh-record-exchange.md)에 기록한다.

실제 두 PC 사이의 방화벽·공유기·절전·ARM64 네이티브 실행과 화면 조작 검증은 배포 전 항목으로 남는다. 전체 방향은 [자동 호스트 설계](automatic-host-design.md)를 따른다.
