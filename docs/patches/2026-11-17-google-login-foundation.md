# 2단계 첫 패치 — Google 로그인 기반

2026-11-17. [개발 계획](../development-direction.md)의 2단계를 시작한다. 이번 범위는 신원 확인·최소 권한·로그인 취소·기기별 로그인 상태다. **이름·설정·팀 목록의 Drive 저장·복원은 아직 구현하지 않았다.** 정식 배포하지 않고 버전은 v0.9.14로 유지한다.

## 사용자에게 달라지는 점

- 빌드에 포함된 Google 연결 정보로 시작한다. 일반 사용자에게 OAuth JSON이나 서버 주소 입력을 요구하지 않는다. 이번 개발 빌드는 기존 설치에서 쓰던 데스크톱 OAuth 클라이언트만 로컬의 Git 제외 설정에 재사용했다. 개인 로그인 토큰·API 키·팀 자료는 복사하지 않았다.
- 로그인을 시도하면 시스템 브라우저로 Google 인증을 진행한다. 앱에서 기다리지 않고 **로그인 취소**를 누를 수 있다. 해당 요청의 임시 루프백 포트도 닫힌다.
- 과거 형식의 로그인 정보와 이메일 표시값을 새 계정 신원의 근거로 사용하지 않는다. 원본 정보는 새 로그인이 성공하기 전까지 유지하며, 앱에는 재로그인 안내를 표시한다.
- 새 형식의 로그인은 앱을 다시 열면 브라우저 없이 Google에서 계정을 재확인한다. 인터넷 오류 때는 연결 재확인을, 권한 만료 때는 재로그인을 안내한다.
- **이 기기에서 로그아웃**은 이 PC의 보관 정보만 지운다. 다른 PC의 연결을 취소하거나 Drive 자료를 삭제하지 않는다.
- 연결이 완료돼도 팀·설정의 자동 복원이 끝났다고 표시하지 않는다. 팀 파일·공용 AI도 계속 준비 중이다.

## 로그인에서 확인하는 것

시스템 브라우저·루프백·PKCE를 사용하는 [Google 데스크톱 OAuth 흐름](https://developers.google.com/identity/protocols/oauth2/native-app)을 따른다. 32바이트 난수의 PKCE verifier, state, nonce를 각각 만들고 재사용하지 않는다. 첫 로그인에서 요청하는 권한은 `openid`, `email`, `drive.appdata`뿐이다. 기존 계정에 과거의 더 넓은 권한이 남아 있을 수 있으며 이를 자동 취소했다고 주장하지 않는다.

신원은 고정된 Google HTTPS 토큰 엔드포인트의 코드 교환 응답과 Google UserInfo 응답을 함께 확인한다. 토큰 응답의 issuer·audience·authorized party·만료·발급 시각·nonce·subject를 확인하고, access-token hash가 있으면 대조한다. UserInfo의 subject가 같고 이메일이 확인돼 있어야 연결을 저장한다. 이메일이 바뀌어도 같은 subject는 같은 계정이며, refresh 과정에서 다른 subject가 나오면 거부한다. 이메일 문자열을 계정 ID로 쓰지 않는다. 기준은 [Google OpenID Connect 문서](https://developers.google.com/identity/openid-connect/openid-connect)와 [공식 Discovery 엔드포인트](https://accounts.google.com/.well-known/openid-configuration)다.

이 패치는 Google와 직접 통신해 받은 응답을 다룬다. **외부에서 전달받은 JWT의 독립적인 서명 검증기는 구현하지 않았다.** Google 문서가 구분하는 직접 HTTPS 토큰 응답의 신뢰 경계를 사용한다. 토큰과 UserInfo 요청의 리디렉션은 따르지 않으며 응답 크기와 시간을 제한한다. 신원 해석 함수는 내부 전용이고, 클라이언트가 ID 토큰·subject를 IPC로 보내 인증받는 경로는 없다. 향후 AI 중계 등에서 다른 기기가 보내는 JWT를 받을 때는 이 함수를 재사용하지 않고 독립적인 서명 검증을 구현해야 한다.

현재 권한은 [개인 앱 데이터 공간](https://developers.google.com/workspace/drive/api/guides/appdata)을 위한 최소 범위다. 팀 자료의 파일 권한과 Calendar 동의는 다음 기능 단계에서 검증한다. 설치형 앱에서는 `include_granted_scopes`를 이용하는 증분 인증을 가정하지 않는다. 추가 기능을 켤 때 필요한 권한 집합으로 다시 동의받는 흐름을 별도로 구현해야 한다.

## 실패와 보관 처리

- 코드 교환·신원 확인·권한 확인·보호 저장을 마친 뒤 연결을 교체한다. 실패하면 기존 토큰 값과 로그인 상태를 덮어쓰지 않는다.
- 새 로그인 정보는 Windows DPAPI로 보호한다. 보호 실패 시 평문·base64 저장으로 대체하지 않는다. 새 형식에서도 보호되지 않은 보관 정보는 재로그인을 요구한다.
- 저장소의 원자적 커밋을 추가했다. 디스크 쓰기 실패 시 메모리와 원본의 기존 값도 유지한다. 검증이 끝나기 전에 연결 완료로 표시하지 않는다.
- 유효하지 않은 state·Host·중복 응답 인자·잘못된 issuer·다른 경로·POST 요청은 로그인 결과로 처리하지 않는다. 잡음 요청 하나가 정상 로그인 요청을 취소하지 않는다. 연결별 읽기와 전체 대기 시간을 제한한다.
- 취소는 현재 시도에만 적용한다. 다음 로그인 시도에 취소 신호가 남지 않는다. 저장을 완료한 뒤 브라우저의 완료 페이지 전송이 늦는 상황을 로그인 취소로 오인하지 않는다.
- Google 오류 원문, 토큰, 인증 코드, 이메일을 루프백 완료 페이지나 오류 메시지에 반사하지 않는다. 현재 PC 로그아웃에서 Google의 전역 revoke API를 호출하지 않는다.
- 기존 Firebase 계정 백업·팀 캐시·대화·공유 대기함을 Google에 업로드하지 않는다. `resume`은 로그인 신원 확인만 수행하며 과거 팀 복원 함수를 호출하지 않는다.

## 확인한 결과와 한계

- Windows x64 전체 테스트 **78개 통과**, 기존 실계정 Firebase 검사 **3개 제외**. 새 로그인 관련 검사 15개를 포함한다. 완료 페이지 전송 변경 후 해당 로그인 검사 4개도 다시 통과했다.
- 권한 범위, PKCE·state·nonce, issuer·audience·시각·access-token hash, UserInfo 계정 불일치, 확인되지 않은 이메일, 부족한 권한, 과거 형식 거부를 검사했다.
- 같은 subject의 이메일 변경, 다른 subject의 refresh 거부, 만료된 refresh, 보호된 토큰 저장, 로컬 로그아웃의 추가 네트워크 호출 없음, 디스크 실패 때 원본·메모리 보존, 오류 원문 비노출을 검사했다.
- 모형 Google 엔드포인트와 실제 루프백 소켓으로 로그인 완료, 잘못된 응답 무시, 취소·포트 종료·다음 시도의 독립성, 코드 교환 도중 취소를 검사했다. 이를 실제 Google 로그인 성공이나 Google 앱 공개 검증으로 간주하지 않는다.
- WebAssembly 화면과 Windows x64 앱 빌드를 통과했다. 실제 계정의 새 로그인 동의·장기 갱신·다른 PC 복원은 이번에 자동 수행하지 않았다. Google 인증 화면은 사용자가 직접 조작해야 한다.
- 새 Windows 미리보기에서 별도 설정 입력 없이 활성화된 **Google로 시작하기** 버튼과 권한 안내를 확인했다. 미리보기에는 실제 사용자의 로그인 토큰을 넣지 않았다.

## 다음 연결 작업

1. 검증된 계정 ID별로 이름·기본 설정·팀 폴더 참조와 미전송 변경을 분리한다. 요청 도중 계정이 바뀌면 이전 결과를 새 계정에 적용하지 않는다.
2. 기존 Firebase 백업과 다른 새 형식으로 개인 Drive 앱 공간의 저장·복원을 붙인다. 먼저 원격 자료를 확인하고, 새 PC의 빈 상태로 덮어쓰지 않는다. 실패·재시도·동시 수정을 처리한다.
3. 팀 폴더 만들기·초대·현재 공유 권한 확인을 구현한다. 복원된 참조나 이메일만으로 팀 접근을 허용하지 않는다.
4. 실제 Google 동의와 같은 계정의 다른 PC 복원을 확인한 뒤 2단계 완료를 판단한다.
