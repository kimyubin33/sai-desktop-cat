# 연결된 내 일정 확인·수정·삭제 — 2026-11-17

## 이번 패치

[기본 캘린더 추가](2026-11-17-my-calendar.md)에 **등록된 일정 조회 → 현재 내용과 업무 비교 → 확인한 수정·삭제**를 연결했다. Calendar의 권한 범위는 추가하지 않았고 기존 별도 연결을 재사용한다. 실제 Google 계정의 일정 변경·실제 OAuth 승인·Claude 과금 호출·서비스 배포는 하지 않았다.

### 사용자 동작

1. 협업의 **내 일정**을 누르면 현재 계정·최신 업무와 해당 할 일의 기본 캘린더 일정을 읽는다. 조회가 실패한 상태를 ‘일정 없음’으로 표시하지 않는다.
2. 업무 제목·반영할 날짜와 **현재 Calendar 일정**을 비교한다. 현재 Calendar에서 직접 바꾼 제목·날짜도 그대로 보여 준다. 확인 후 업무 제목과 선택한 날짜로 수정한다. 변경할 내용이 같으면 수정 요청을 보내지 않는다.
3. 삭제는 **연결된 일정 삭제**를 펼치고 별도 확인을 거친다. 내 Calendar 일정만 삭제하며 팀의 할 일과 Drive 파일은 유지한다. 완료한 업무에서도 기존 일정을 확인·삭제할 수 있고, 새 일정 추가·수정은 하지 않는다.
4. 미리보기를 새로 읽으면 확인 체크를 초기화하고 입력한 날짜는 유지한다. 날짜를 다시 바꿔도 확인 체크를 초기화한다. 업무가 바뀌었다고 일정을 자동 수정·삭제하지 않는다.

### 관리할 수 있는 일정

현재 Google 계정의 기본 캘린더에서, 기존의 계정·팀·업무 지문과 앱 표시가 일치하는 **하루짜리 종일 일정**만 수정·삭제한다. 시간이 지정됐거나 여러 날·반복·참석자·추가 메모·위치·첨부·회의 등이 있는 일정, 잠긴 일정과 버전 확인이 불가능한 일정은 표시만 하고 Calendar에서 직접 관리하도록 안내한다. 다른 캘린더 선택·팀원 초대·자동 등록·복잡한 일정 편집으로 범위를 넓히지 않았다.

## 변경 보호와 재확인

- 네이티브 메모리에 현재 계정 subject·epoch·팀·업무·협업 변경 번호·업무 제목·Google 일정 ETag를 결속한 확인 번호를 만든다. 화면에는 ETag나 Google 일정의 사적 메타데이터를 보내지 않는다. 최대 8개를 보관하고 생성 후 15분간 사용할 수 있다. 닫기·로그아웃·프로세스 종료와 다음 미리보기의 만료 정리 때 제거하며, 메모리의 보안 삭제를 보장하는 방식은 아니다.
- 실행 전 현재 팀 권한과 업무 변경 번호, 일정 출처·형식·ETag를 확인하고 외부 쓰기 직전에 업무를 다시 읽는다. Drive 확인과 Calendar 쓰기를 하나의 원자적 트랜잭션으로 만드는 것은 아니므로 그 사이 팀 권한이 바뀌는 분산 시스템의 경계는 남는다.
- PATCH와 DELETE에는 **확인한 ETag의 If-Match**를 반드시 보낸다. 그 사이 다른 변경이 있으면 Google의 412 응답으로 멈추고, 새 버전을 자동으로 받아 덮어쓰지 않는다. 와일드카드·약한 태그·헤더 주입 형태를 허용하지 않는다. 주소는 현재 계정의 기본 캘린더와 결정적인 업무별 일정 ID로만 구성한다.
- PATCH는 제목·시작/종료 날짜와 사적 작업 표시만 변경한다. 다른 사적 속성을 유지하고 사용자가 바꾼 알림 설정 등을 초기화하지 않는다. 원문·AI 요약·API 키·Google 토큰을 일정에 넣지 않는다.
- 변경 시도는 전송 직전에 메모리에 기록한다. 같은 확인 번호를 다시 실행해도 PATCH·DELETE를 반복하지 않고 결과만 읽는다. 다른 날짜나 삭제 작업으로 같은 번호를 재사용할 수 없다.
- PATCH에는 임의의 작업 번호를 사적 속성에 남겨 응답이 유실돼도 해당 변경과 확인한 제목·날짜를 조회로 대조한다. DELETE의 빈 성공 응답도 처리하며, 이후 취소/삭제/부재 상태를 조회한다. 다른 사람이 삭제했는지까지 판별해 ‘내 요청이 삭제했다’고 주장하지 않고, 현재 일정이 없는 상태를 확인했다고 표시한다.
- **전송 결과 다시 확인**은 별도의 조회 전용 IPC다. 최초 요청이 전송 전에 실패한 경우에도 수정·삭제를 뒤늦게 실행하지 않는다. 요청 전 중단·응답 유실·다른 변경을 구분해 알리고, 새 변경은 최신 미리보기와 새 확인을 거쳐야 한다.
- 앱 재시작·창 닫기·확인 만료 뒤에는 이전 작업 번호를 자동 재전송하지 않는다. 새 미리보기로 실제 Calendar 상태를 확인한다. 이미 보낸 외부 변경은 창을 닫는 것으로 취소되지 않으며, 새 계정에 이전 결과를 표시하지 않는다.
- Google이 삭제 상태를 반환한 일정은 새로 만들지 않는다. 과거 삭제 이력이 더 이상 조회되지 않는 404와 처음부터 없는 일정의 구분 한계는 [이전 패치](2026-11-17-my-calendar.md)와 같다.

## 검증

- `cargo test --locked --workspace --target x86_64-pc-windows-msvc -- --test-threads=4`: **198개 통과**(core 192, native 4, UI 2). 기존 Firebase 실계정 검사 3개는 제외 상태다.
- `node --test services/team-ai/gateway.test.mjs`: **17개 통과**. 전체 자동 검사 **215개**다.
- 새 검사 **13개**(흐름 12개, 조건부 요청 검사 1개): 현재 일정 표시·사적 필드 비노출, 검토한 제목/날짜만 변경, 사적 속성·알림 보존, 완료 업무의 일정만 삭제, 변경 없음·조회 전용 재확인의 무변경, 미리보기 후 사용자 변경, GET과 쓰기 사이의 412, 수정·삭제 응답 유실, 응답과 조회가 함께 실패한 뒤 재확인, 두 확인 세션의 동시 변경, 복잡한 일정/버전 누락, 업무·권한·계정·팀·닫기 격리, 실패·다른 출처를 부재로 취급하지 않음을 확인했다. 모의 서버가 실제 If-Match 헤더를 검사하고 DELETE에는 빈 204 응답을 반환한다.
- Wasm 화면 빌드와 Windows x64 개발 빌드를 통과했다. 가짜 Google 계정과 루프백 서버만 사용했으며, 위 동시성 검사는 Google 실서비스의 두 PC 검증을 대신하지 않는다.
- 자격 증명 없는 Chrome 가상 자료 화면에서 업무 제목/날짜와 현재 일정 비교, 확인 전 수정 비활성화, 수정 후 현재 내용 갱신과 확인 초기화, 삭제 영역의 기본 접힘·별도 확인, 삭제 후 재생성 버튼이 없는 상태를 확인했다. 실제 인증·개인정보 권한 창은 조작하지 않았다.

## 남은 작업

Google 실계정·두 PC에서 실제 ETag와 412, 반복 요청·권한 철회·시간대·기본 캘린더 공유 설정·빈 DELETE 응답·통신 중단을 검증해야 한다. 현재 운영용 팀 AI는 여전히 미배포이고 모델·예산·운영 위치 결정도 별도다. 다른 캘린더 선택·시간 지정·자동화는 후속 기능이며 5단계 전체 완료나 정식 배포로 표시하지 않는다. 다음 검증은 설치부터 계정/팀 복원·파일·협업·일정까지 이어지는 전체 사용자 흐름에 맞춘다.
