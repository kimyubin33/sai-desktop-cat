# 검토한 할 일을 내 기본 캘린더에 추가 — 2026-11-17

## 범위와 사용 흐름

5단계의 첫 Calendar 패치다. 협업 할 일의 **내 일정 ＋ → 날짜 확인 → 내 기본 캘린더에 추가**를 구현했다. AI로 검토해 저장한 할 일과 직접 만든 할 일 모두 사용할 수 있다. AI 중계 서비스와 독립적으로 동작하는 경로이며, 이번에도 실제 Google 인증·일정 변경·Claude 과금 호출은 하지 않았다.

1. 협업에서 동시 변경이 없고 완료 전인 할 일의 **내 일정**을 누른다.
2. 최신 제목과 현재 Google 계정, 날짜를 확인한다. 마감일이 있으면 제안하되 사용자가 바꿀 수 있다. 마감일이 없으면 날짜를 직접 고른다.
3. Calendar를 처음 사용할 때만 현재 Google 계정으로 추가 일정 권한을 연결한다. 기존 Drive 로그인은 교체하지 않는다. 정상 연결은 저장·갱신해 재사용하며, 거절·철회·만료·다른 PC에서는 연결이 다시 필요할 수 있다.
4. 제목·날짜·등록 계정을 확인한 뒤 직접 추가한다. 본인의 기본 캘린더에 하루짜리 **종일 일정**으로 만들며 다른 팀원을 초대하지 않는다. 담당자 이름은 Google 계정으로 추측하지 않는다.

대상은 현재 계정의 **기본 캘린더 하나**다. 다른 캘린더 선택, 시간 지정, 자동 등록, 팀 변경·완료에 따른 일정 수정·삭제, 앱에서 삭제된 일정의 재생성 선택은 후속 범위다. 이번 패치로 5단계 전체를 완료했다고 표시하지 않는다.

## 권한과 개인정보

- 첫 Google 로그인에 Calendar 권한을 넣지 않는다. 별도 OAuth 목적에서 `openid email calendar.events.owned`를 요청하고 `include_granted_scopes=false`를 지정한다. 이 권한은 **내 소유 캘린더의 일정 읽기·쓰기·삭제가 가능한 넓은 권한**이며 앱이 만든 일정에만 제한된 Google 권한은 아니다. 앱 구현은 기본 캘린더의 해당 할 일 번호에 대한 GET·POST만 사용하고 다른 일정 목록·상세는 조회하지 않는다.
- 고정된 Google HTTPS 토큰·UserInfo 응답과 nonce·PKCE·state를 확인하고 현재 로그인한 Google subject와 일치해야 연결한다. 다른 계정 선택·권한 거절·잘못된 응답이면 기존 로그인과 연결을 보존한다.
- Calendar 토큰은 별도 `googleCalendarTokensEnc`에 Windows DPAPI로 보호하고 계정·OAuth 클라이언트에 결속한다. 화면·팀 Drive·AI 중계로 전달하지 않는다. 이 PC에서 로그아웃하면 Drive와 Calendar의 보호된 로그인 정보를 함께 지운다. Google 전체 권한이나 다른 PC의 토큰을 철회하는 동작은 아니다.
- Google이 기본 Drive 토큰에 Calendar 범위까지 반환하는 경우에도 범위를 검사해 **팀 AI 중계 전송을 거부**한다. 별도 토큰을 저장했다는 이유만으로 Google의 권한 결합 동작까지 보장하지 않는다.
- Calendar에는 확인한 제목·날짜와 불투명한 출처 지문만 보낸다. 원문·AI 요약·근거·담당자 이름·팀원 이메일은 보내지 않는다. 참석자·회의·메일 초대를 만들지 않으며, 일정 알림은 기본값을 사용하지 않도록 지정한다. 일정은 `private`와 `transparent`로 추가한다. Google Calendar의 공유·관리자 정책에 따른 열람까지 차단하거나 종단 간 암호화를 제공하는 기능은 아니다.

## 중복·충돌·실패

- 계정 subject·팀 폴더 ID·안정적인 할 일 ID로 결정적인 일정 ID를 만든다. 제목·날짜를 바꿔도 새 번호를 만들지 않는다. Google이 허용하는 base32hex 문자 범위 안의 ID를 사용한다.
- 매번 현재 Drive 권한과 최신 협업 변경 번호를 검사한다. 동시 변경·완료·오래된 미리보기·다른 팀 요청은 거부한다. 팀 보기 권한으로도 본인 일정은 추가할 수 있다. 외부 쓰기 직전에 협업을 다시 확인하되 Drive 읽기와 Calendar 쓰기가 하나의 원자적 트랜잭션인 것은 아니다.
- 먼저 같은 ID를 조회한다. 기존 일정이 있으면 현재 제목·날짜를 알리고 그대로 보존한다. 사용자가 Calendar에서 날짜·제목·시간을 수정해도 덮어쓰지 않는다. 다른 출처의 일정이면 거부한다.
- 새 일정은 같은 ID로 한 번 POST한다. 동시 생성의 409 응답은 같은 ID 조회로 확인한다. 응답 유실·503·확인 실패는 성공으로 표시하지 않으며, 사용자가 다시 누르면 먼저 같은 ID를 조회한다. 앱 재시작이나 두 로컬 저장소에서도 ID가 바뀌지 않는다. 실제 Google의 분산 생성 동작과 두 PC 검증은 남아 있다.
- Google이 삭제 상태(`cancelled` 또는 410)를 반환하면 다시 만들지 않는다. 404와 과거 삭제 이력이 항상 구분되는 것은 아니므로 모든 삭제 이력의 영구 감지를 보장하지 않는다. 백그라운드 재생성은 없다.
- 오프라인 전송 대기·자동 재시도·자동 일정 갱신은 추가하지 않았다. 창을 닫아도 이미 보낸 외부 등록이 취소되는 것은 아니며, 계정이 바뀐 뒤에는 이전 결과를 새 계정 화면에 반영하지 않는다. 불확실한 등록은 해당 계정의 Calendar에서도 확인해야 한다.
- 향후 수정·삭제는 앱 출처와 당시 상태를 확인하고 ETag/If-Match로 사용자가 바꾼 일정을 보호하는 별도 단계로 구현한다.

## 검증

- `cargo test --locked --workspace --target x86_64-pc-windows-msvc -- --test-threads=4`: **185개 통과**(core 179, native 4, UI 2). 이전 Firebase 실계정 검사 3개는 제외 상태다.
- `node --test services/team-ai/gateway.test.mjs`: **17개 통과**. 전체 자동 검사 **202개**다.
- 새 검사 **17개**: 별도 동의 URL·토큰 보호·연결 재사용·권한 거절·신원/nonce 불일치·재시작 갱신·철회·계정/epoch 격리·중계의 Calendar 범위 거부, 전체 OAuth 루프백 완료·취소, 명시적 날짜·종일 종료일, 미동의·미연결, 응답 유실·다른 로컬 저장소·동시 생성, 사용자 수정·삭제 보존, 오래된/완료/동시 변경/다른 팀 업무, 전송 직전 권한 취소, 위조 대상·잘못된 날짜·다른 출처 일정을 확인했다. 모두 가짜 계정과 모의 Google 서버다.
- Wasm 화면 빌드와 Windows x64 개발 빌드를 통과했다. `git diff --check`도 통과했다.
- 자격 증명 없는 로컬 Chrome 가상 화면에서 협업 버튼, 계정·날짜 표시, 확인 전 비활성화, 확인 후 등록·결과 표시·재전송 비활성화를 확인했다. 실제 OAuth 승인 화면은 조작하지 않았다.

## 남은 검증과 다음 범위

개발 측 Google 프로젝트의 Calendar API 사용 가능 여부·동의 화면의 범위와 앱 검증 상태, 실제 계정의 최초 동의/거절/철회·재시작, 같은 계정 두 PC의 동시 등록·응답 유실·기본 캘린더·시간대·삭제 보존을 확인해야 한다. 일반 사용자에게 Firebase·서버·Google 클라이언트 JSON 설정을 요구하는 기능은 추가하지 않았다.

다음 구현은 Calendar에서 이미 연결된 상태를 미리 보여 주고, 사용자가 검토한 수정·삭제를 원본 변경과 충돌 없이 처리하는 흐름이다. 대상 캘린더 선택과 자동화 범위는 그 뒤에 확장한다. 팀 AI 서비스의 모델·예산·운영 위치 결정과 실제 배포도 별도 미완료 상태다.
