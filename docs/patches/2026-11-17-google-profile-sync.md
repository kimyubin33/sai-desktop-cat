# 2단계 두 번째 패치 — 이름과 기본 설정의 Drive 동기화

2026-11-17. [개발 계획](../development-direction.md)의 2단계를 이어간다. 사용자 서버나 Firebase 설정 없이, 확인한 Google 계정의 앱 전용 저장 공간에 이름과 기본 설정을 저장하는 실행 경로를 연결했다. **실제 Google 계정과 두 PC의 검증은 아직 완료하지 않았다.** 정식 릴리스·버전 변경·배포는 하지 않는다.

## 이번 사용자 흐름

1. 앱에서 Google 로그인 또는 기존 연결 재확인을 마친다.
2. 계정의 기존 설정을 먼저 읽는다. 처음 실행한 PC의 빈 값은 업로드하지 않는다.
3. 설정의 **어디서나 같은 사이**에서 내 이름·고양이 이름·말 거는 빈도를 저장한다.
4. 변경 내용은 이 PC에 먼저 보관하고 Drive로 전송한다. 실행 중 60초마다 확인하며, 저장 직후·로그인 직후·수동 동기화에서도 확인한다.
5. 같은 계정의 다른 PC는 로그인 후 이 설정을 읽는다. 저장 실패·대기 중·확인 완료를 구분한다. 처음 읽기가 실패하면 편집을 막고 재시도할 수 있다.

개인 AI 키·모델 설정·대화 기록·대화 보관 기간·인증 정보·PC 위치·이전 Firebase 자료는 이 동기화에 포함하지 않는다. 기본 설정은 메모리에만 덧입혀 적용하며 로컬 공통 설정 파일에 계정 값을 복사하지 않는다. 로그아웃하거나 새 계정으로 로그인하면 덧입힌 값을 지우므로 A의 이름과 빈도가 B의 기본값이 되지 않는다.

## 변경 저장과 충돌 처리

- 기존 Firebase 계정 백업과 다른 이름·형식의 `sai-profile-v1-*.json` 변경 기록을 사용한다. Drive의 `appDataFolder`에만 저장하며 기존 파일을 PATCH하거나 삭제하지 않는다.
- 변경은 검증된 Google subject에 묶는다. 이메일·프런트엔드가 보낸 계정 ID를 저장 권한의 근거로 사용하지 않는다. 로컬 사본과 대기열도 subject 해시별로 분리한다.
- 설치별 난수 ID와 계정별 변경 순번을 사용한다. Windows 로밍 설정과 다른 `app_local_data_dir`에 설치 ID·대기열을 저장한다. 시스템 시계가 다른 PC에서도 항목별로 병합한다.
- 두 PC가 서로 다른 항목을 바꾸면 두 변경을 유지한다. 같은 항목을 동시에 바꾸면 순번·설치 ID·변경 ID의 정해진 순서로 같은 결과를 선택하며 이전 변경 기록도 남는다. 사용자에게 보인 시간만으로 승자를 정하지 않는다.
- 최초 읽기를 마친 계정의 변경만 대기열에 넣는다. 대기열 커밋이 실패하면 저장 성공으로 응답하지 않는다. 새 PC에서 기존 로컬 설정을 자동 업로드하지 않는다.
- Drive 파일 ID를 미리 발급받아 대기열에 먼저 보관한다. 업로드 응답이 끊기면 같은 ID를 읽고 내용을 대조한 뒤 처리한다. 재시도에서 새 파일을 계속 만들지 않는다. 같은 ID의 내용이 다르면 덮어쓰지 않고 중단한다.
- 동기화를 시작할 때 계정과 토큰을 고정한다. 각 요청과 로컬 반영 때 계정 연결 세대를 확인한다. 로그아웃 전에 시작한 A의 요청이 늦게 끝나도 B의 토큰으로 전송하거나 B의 설정에 반영하지 않는다. 이전 계정 화면의 저장 요청도 거절한다.
- 알 수 없는 필드·버전, 손상된 자료, 다른 subject, 같은 변경 ID의 서로 다른 내용, 불완전한 목록·반복 페이지는 빈 자료로 취급하지 않는다. 기존 사본과 대기열을 보존한다.

팀 폴더 참조의 병합·삭제 표시는 내부 자료 형식과 검사에만 포함했다. 삭제와 같은 순번의 추가가 겹치면 삭제를 우선하며, 더 나중의 명시적인 재참여는 허용한다. 복원된 참조는 항상 `accessVerified: false`다. **팀 만들기·초대·참여·현재 Drive 권한 확인 UI는 아직 없으며 팀 접근을 허용하지 않는다.** 이전 Firebase 팀도 이 형식으로 자동 변환하지 않는다.

## 검증과 제한

자동 검사 전체 **89개 통과**, 기존 Firebase 실서비스 검사 3개는 실행 제외했다. 이번 동기화의 모의 Google HTTP 검사 11개는 다음을 포함한다.

- 빈 새 PC의 읽기에서 업로드가 발생하지 않음, 개인 키·보관 기간이 전송되지 않음.
- 두 PC의 오프라인 변경 병합, 같은 항목의 결정 순서, 팀 참조 삭제·재참여.
- 최초 읽기 실패 시 편집·업로드 중단, 다른 계정의 원격 자료 수신 시 대기 변경 유지.
- 서버가 저장한 뒤 오류를 응답하는 상황에서 앱 재시작 후 같은 파일 ID로 확인하고 중복 생성하지 않음.
- 계정 전환에서 이름·대기열 분리, 이전 화면 저장 거절, 원격 읽기 도중 로그아웃하면 이전 계정 반영 중단.
- 계정 설정이 로컬 공통 설정 파일에 섞이지 않음, 손상된 로컬 사본을 덮어쓰지 않음.

Wasm UI와 x64 Windows 실행 파일 빌드를 확인했다. 이 검사는 실제 Google 동의·API 활성화·배포 OAuth 상태·실제 두 PC의 동작을 대신하지 않는다. 테스트에 사용한 로그인·Drive 응답은 모의 자료이며 실사용자의 토큰·대화는 복사하지 않았다.

실제 자료와 분리한 미리보기 실행에서 파일 → 설정 전환과 로그인 전 로컬 설정 저장을 확인했다. 이 과정에서 설정 쓰기 잠금 안에서 Google 상태를 다시 읽어 저장이 멈추는 문제를 발견해 상태 확인을 잠금 밖으로 옮겼다. 수정한 실행 파일에서 **변경 사항을 저장했어요** 표시까지 재확인했다. Google 로그인 버튼은 누르지 않았고, 로그인 후 계정 설정 화면의 실계정 검증을 완료한 것으로 간주하지 않는다.

현재는 계정당 최대 4,096개 변경 파일로 제한하고, 목록·응답 크기와 요청 시간을 제한한다. 전체 변경을 읽는 초기 구현이므로 정식 배포 전에 변경 목록 캐시·효율적인 조회·안전한 압축 정책과 용량·지연을 검증해야 한다. 한도에 이르면 자동 삭제하거나 조용히 일부만 복원하지 않는다. 앱을 끄면 새 동기화는 실행되지 않는다. 사용자가 Google에서 앱 자료를 지웠을 때 모든 PC의 로컬 사본까지 지우는 기능은 아직 없다.

다음 구현은 **최소 Drive 권한에서 팀 폴더 만들기·초대·접근 확인**이다. 실제 계정의 권한 거절·만료·공유 해제·새 PC 복원은 2단계 완료 전에 확인하고 기록한다.

## 구현 근거

- [Google 앱 전용 저장 공간](https://developers.google.com/workspace/drive/api/guides/appdata): 개인 앱 자료용이며 팀 공유 폴더로 사용하지 않는다.
- [파일 ID 사전 발급](https://developers.google.com/workspace/drive/api/reference/rest/v3/files/generateIds): `space=appDataFolder`와 `drive.appdata` 범위를 사용한다.
- [Drive 업로드](https://developers.google.com/workspace/drive/api/guides/manage-uploads): 메타데이터와 JSON 변경 내용을 multipart 업로드로 생성한다.
