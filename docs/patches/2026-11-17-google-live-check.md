## 증거와 구분

실제 앱의 Windows 파일 선택창과 저장창을 사용했다. `target/google-live-check/`에 합성 원본, A/B 다운로드, 비식별 결과 `result.json`을 보관했다. 로컬 해시 대조로 두 다운로드의 내용 일치를 확인했다. 앱 오류 로그는 확인 시 0바이트였다.

Google 토큰·키를 복호화하거나 출력하지 않았고 사용자 자료 본문도 도구로 읽거나 결과에 기록하지 않았다. Calendar 후속 진단에서는 검증용 설정 파일에 보호된 연결 정보가 존재하는지만 확인했다. 계정 이메일·Google 파일 ID도 이 문서에 넣지 않았다. 기존에 연결된 계정을 재사용했으므로 **초기 Google 로그인 화면·새 기기의 OAuth 승인·두 PC 복원 검증**을 통과한 것으로 표시하지 않는다.

화면 검사 도구 연결이 한 번 끊긴 뒤 창을 다시 선택해 복구했다. 협업 저장 전에 선택한 팀이 검증 A임을 확인했다. 날짜 선택기의 포인터 입력은 도구의 창 소유 확인에 막혀, 해당 앱의 키보드 입력으로 날짜를 선택하고 최종 필드 값이 `2026-11-20`인지 확인했다. 이 도구 문제를 앱 오류로 보고하거나 앱 보호 로직을 완화하지 않았다.

이번 변경은 실제 검증 결과를 문서에 반영한 것이며 실행 코드는 바꾸지 않았다. 새 기능 테스트나 전체 모의 테스트를 반복하지 않았고, 실제 전송·파일 해시·업무 화면을 확인했다. 공용 Claude 호출·배포·과금이나 정식 릴리스도 실행하지 않았다.

## Calendar 사용자 확인과 후속 재실행 검사

검증 업무의 **내 일정으로 이어가기** 창을 열고, 제목과 `2026-11-20` 날짜를 표시한 상태로 준비했다. 최초 확인 당시 연결에는 Calendar 권한이 없어서 도구로 일정 등록·수정·삭제를 시험하지 않았다. 사용자에게 **내 Calendar 연결**을 직접 수행하도록 요청했다.

[컴퓨터 사용 스킬](C:/Users/speed/.codex/plugins/cache/openai-bundled/computer-use/26.1111.21308/skills/computer-use/SKILL.md)이 참조하는 [실행 지침](C:/Users/speed/.codex/plugins/cache/openai-bundled/computer-use/26.1111.21308/docs/guidance.md)에 **“Do not automate user authentication dialogs.”**라고 명시돼 있다. 따라서 Google 계정 선택과 최초 권한 동의는 사용자가 직접 진행한다. 이는 앱이 임의로 로그인이나 권한을 생략할 수 없다는 뜻이며, 이번 정상 파일 작업에서는 저장된 연결을 재사용했다.

사용자는 연결·검증 일정 등록을 완료했다고 응답했고, 등록한 곳이 **사이 앱의 ‘내 캘린더에 추가’**라고 확인했다. 그러나 확인 중인 미리보기 창은 여전히 **내 Calendar 연결**을 표시했다. 조회 전용 **최신 내용 확인**을 누른 뒤에도 같은 상태였다. 이 검증 앱은 `target/google-login-preview-data`를 사용하며, 기본 미리보기의 자료 공간과 구분된다. 어느 실행본에서 등록했는지와 연결 정보가 남지 않은 원인은 확인되지 않았다.

검증 앱을 정상 종료하고 같은 자료 공간으로 재실행했다. 처음에는 샌드박스에서 실행된 프로세스의 창을 화면 도구가 찾지 못해, 그 검증 프로세스만 종료하고 사용자 화면에서 다시 실행했다. 새 창은 발견했지만 화면 도구의 활성화·조회가 **`foreground window did not report a process id`** 오류로 실패했다. 창을 다시 선택한 재시도도 실패해 추가 UI 입력을 중단했다. 실행 중인 앱의 오류 로그는 0바이트였으며, 이 오류를 Calendar API 실패로 간주하지 않는다.

재실행한 검증 자료 공간의 설정에는 보호된 Calendar 연결 정보가 없었다. 비밀값을 복호화하지 않고 필드의 존재와 보호 형식 여부만 확인했다. 이는 **이 저장소에서 연결 정보를 확인하지 못했다**는 증거이며, 사용자가 다른 실행본에서 등록한 일정의 존재 여부를 증명하지 않는다. 새 Google 인증이나 일정 추가·수정·삭제는 수행하지 않았다.

사용자는 재확인 질문에 연결 버튼이 보인다고 응답한 뒤, 최종적으로 **“아 작동 합니다.”**라고 정상 동작을 확인했다. 이 최종 응답을 사용자 확인 결과로 반영하고 현재 문제 조사를 마친다. 앞서 관측한 미연결 상태를 현재도 계속되는 장애로 단정하지 않는다. 원인이 재현되지 않았으므로 인증·저장 코드는 변경하지 않았다.

이 시점에는 앱에서의 연결·등록은 **사용자 확인**, 기존 일정의 제목·날짜·중복 방지와 Calendar 연결의 재실행 후 재사용은 **독립 검증 미완료**로 구분했다. 아래 후속 검사에서 확보한 증거를 별도로 기록한다.

### 후속: 연결 재사용과 삭제 상태 조회 확인

같은 미리보기 창을 다시 선택하자 화면 검사가 가능해졌다. 검증 A의 위 할 일에서 **내 일정 +**를 열었고, 추가 로그인·동의 없이 Calendar 조회를 마쳤다. 버튼은 **일정 권한 확인**으로 표시됐으며 결과는 **삭제된 일정이에요. 자동으로 다시 만들지 않아요.**였다. 삭제한 사람·시점·경로는 확인하지 않았다. 이 검사에서 삭제 작업을 실행하지 않았다.

미리보기를 정상 종료하고 프로세스 종료를 확인한 뒤, 같은 실행 파일과 `target/google-login-preview-data`로 재실행했다. Google 연결과 검증 A/B 팀 카드가 복원됐고, 검증 A의 할 일 제목·`2026-11-20` 마감일·시작 전 상태와 최신 Drive 확인 표시도 유지됐다. 같은 할 일의 Calendar 창을 열자 추가 Google 로그인·동의 없이 다시 삭제 상태를 조회했다. **최신 내용 확인**으로 재조회해도 같은 상태였다.

따라서 **한 계정·한 PC에서 Calendar 연결의 재실행 후 재사용**, **새 검증 팀·업무 복원**, **삭제 상태의 재조회와 생성 기능 차단**을 실제 앱 화면으로 확인했다. 삭제 상태에서는 날짜 입력이 비활성화되고 일정 추가·수정·삭제 항목이 표시되지 않았다. Calendar 미리보기와 새로고침은 해당 할 일의 고정된 일정 번호를 GET으로 조회하는 코드 경로다. 이 후속 검사에서 일정 생성·수정·삭제 요청은 실행하지 않았다.

이 삭제 상태 검사에서 표시된 제목·날짜는 **협업 할 일의 값**이다. 삭제 상태 응답으로 정상 Calendar 일정의 제목·날짜 보존이나 전체 캘린더의 중복 개수를 확인했다고 주장하지 않는다. 이어 아래 정상 일정 검사를 별도로 진행했다.
