# PC 팀 장치 신원과 관리자 승인

> 이전 장치 승인 구조의 기록입니다. 2026-11-17의 [새 개발 방향](development-direction.md)이 우선하며, 사용자에게 장치 승인 파일과 연결 정보를 다루게 하는 흐름은 제거 대상입니다. 기존 자료 보존과 기능 코드 제거는 구분해 진행합니다.

자동 호스트 설계의 단계 1 중 장치 신원과 승인 이력을 구현했다. 외부 조정 서비스나 별도 연결 프로그램 없이 각 PC에서 준비할 수 있다. 이 단계의 개발·자동 검증에는 두 번째 PC가 필요하지 않다. 실제 두 PC 사이의 연결·방화벽·절전 검증은 배포 전 별도 항목으로 남긴다.

## 1. 이번에 구현한 범위

| 항목 | 동작 |
|---|---|
| 장치 신원 | Ed25519 서명 키와 별도 X25519 암호화 키 생성. 두 공개키를 묶은 장치 ID를 재시작 후에도 유지 |
| 운영 관리자 | 장치 키와 분리된 Ed25519 승인 키. 한 저장소의 모든 PC 팀에서 같은 관리자 키 사용 |
| 장치 등록 | 장치가 서명한 등록 요청을 관리자가 확인하고 서명해 승인 |
| 등록 해제 | 관리자가 서명한 해제 이력을 추가. 같은 요청의 재사용 차단 |
| 승인 이력 | 팀 ID·순번·이전 해시·관리자 서명을 검증. 서로 다른 이력은 거부 |
| 로컬 저장 | SQLite 트랜잭션으로 키·공개 신원 기록·승인 이력을 보관 |
| 키 보호 | Windows 현재 사용자 계정의 DPAPI 사용. 보호 실패 시 평문·raw 저장으로 대체하지 않음 |
| 설정 화면 | 장치 생성, 팀 준비, 공개 요청·승인 정보 복사, 승인·해제, 지문 확인 |

신원 자료는 기존 Firebase·고정 PC 서버의 사용자·팀과 아직 연결하지 않는다. 단계 0 연결 실험은 기존 임시 인증서와 공개 카드를 계속 사용한다. 11월 16일 [승인 장치 연결과 로컬 톡 원본](mesh-local-log.md)에 이어 [수신 장치별 암호화·준비 톡 교환·상대 저장 확인](mesh-record-exchange.md)을 추가했다. 자동 호스트 선택과 제3자 기록 복제는 후속 구현이다. 기존 팀 톡까지 새 모드의 암호화·전송으로 전환되었다고 표시하지 않는다.

## 2. 설정 화면의 준비 흐름

일반 사이 앱의 **설정 → PC 팀 장치 등록 준비 → 내 장치와 관리자 승인 정보**에서 연다. 별도 `Sai-Connection-Test.exe`는 연결 진단 전용이며 이 기능을 제공하지 않는다.

### 관리자 PC

1. `내 장치 만들기`를 누른다. 같은 버튼의 내부 명령을 다시 실행해도 기존 신원을 사용한다.
2. PC 팀 이름을 넣고 `새 PC 팀 준비 (관리자)`를 누른다. 관리자 키를 처음 만들고, 자기 장치를 승인한 팀 정보를 만든다. 이후 팀도 같은 관리자 키를 사용한다.
3. `전달할 공개 자료`의 승인 정보와 관리자 지문을 팀원에게 전달한다.
4. 팀원의 등록 요청을 `받은 등록 요청 또는 승인 정보`에 붙여 넣고, 해당 요청이 등록하려는 사람의 것인지 확인한 뒤 `장치 등록 승인 (관리자)`를 누른다.
5. 갱신된 공개 승인 정보를 팀원에게 돌려준다.

### 팀원 PC

1. `내 장치 만들기`를 누른다.
2. 관리자가 준 최초 승인 정보를 붙여 넣는다. 관리자 화면이나 이미 신뢰하는 연락 경로에서 지문을 직접 대조하고, 지문 입력란에 넣어 `승인 정보 등록`을 누른다. 받은 자료 안의 값을 그대로 신뢰 기준으로 삼지 않는다.
3. `내 등록 요청 만들기`를 눌러 공개 요청을 관리자에게 전달한다. 이 요청은 해당 팀·관리자·장치의 두 공개키에 묶여 있다.
4. 관리자가 돌려준 갱신 승인 정보를 등록한다. 장치 목록에서 `내 PC`의 승인 상태를 확인한다.

공개 자료에는 개인키·로그인 토큰을 넣지 않는다. 공개키·장치 ID·팀 이름·등록 이력은 포함하므로, 준비한 팀의 참여자에게 전달한다. 현재의 복사·붙여넣기는 승인 규약을 검증하기 위한 준비 절차이며, 관리자 승인 이력의 팀원 간 자동 전달은 아직 구현하지 않았다. 이미 승인한 장치의 연결 정보는 별도 [LAN 자동 연결](mesh-automatic-connection.md) 모드로 확인할 수 있다.

### 등록 해제와 재등록

관리자는 승인된 장치의 `등록 해제`를 누른 뒤 갱신 승인 정보를 다른 PC에 전달한다. 해제 이력을 받아 저장한 PC는 과거 승인 정보를 다시 받아도 이전 승인 상태로 돌아가지 않는다. 해제 사실을 아직 받지 못한 오프라인 PC에 즉시 적용되는 것은 아니다.

해제한 장치를 다시 승인하려면 장치에서 새 등록 요청을 만든다. 예전에 승인에 사용한 요청을 다시 붙여 넣는 방식은 거부한다. 관리자 키가 없는 PC에서는 승인·해제를 할 수 없고, 이미 신뢰한 운영 관리자를 새 팀 생성이나 다른 관리자의 자료로 교체할 수도 없다.

## 3. 저장과 오류 처리

저장 경로는 앱 데이터 폴더 아래 `mesh/identity.sqlite3`다. 기존 팀 서버별 캐시와 분리한다. 상태 조회만으로 새 DB나 개인키를 만들지 않으며, 사용자의 생성·등록 명령에서 초기화한다.

개인키 봉투는 용도와 버전을 포함해 DPAPI로 보호한다. 암호화된 키와 공개 신원 기록을 같은 트랜잭션에 저장한다. 장치 키와 관리자 키를 바꿔 끼우거나 보호 자료가 손상되면 실패로 처리한다. 공개 기록이 있는데 개인키만 없어져도 새 키를 자동 생성하지 않는다.

SQLite의 WAL, `synchronous=FULL`, 즉시 쓰기 트랜잭션을 사용한다. 동시에 두 요청을 승인하면 쓰기를 직렬화해 서로 다른 순번을 부여한다. 승인 정보 중간 저장에 실패하면 해당 가져오기 전체를 롤백한다. 이미 저장한 이력과 충돌하는 자료도 기존 기록을 바꾸지 않는다.

DPAPI는 디스크에 보관한 키를 보호한다. 같은 Windows 사용자 권한으로 실행되는 악성 프로그램이나 장악된 운영체제로부터 키를 숨긴다고 보장하지 않는다. 복호화 직렬화 버퍼와 소유 중인 개인키 버퍼는 사용 후 지운다. 모든 라이브러리·프로세스 메모리 사본을 지운다는 보장은 하지 않는다.

DB 전체를 삭제하거나 과거 백업으로 바꾼 경우까지 이 로컬 기록으로 탐지하지는 못한다. 관리자 키 복구·이전·교체와 장치 백업 복원 절차는 아직 제공하지 않는다. DB 파일을 다른 PC에 복사하는 것을 키 이전 방법으로 사용하지 않는다.

## 4. 서명 규약과 한도

v1은 정의된 Rust 구조체를 정해진 필드 순서의 UTF-8 JSON으로 직렬화하고, 용도 문자열과 NUL 바이트를 앞에 붙여 서명한다. 임의 JSON 문자열 자체나 일반적인 JSON 정규화 규약에 서명하는 방식이 아니다. 입력은 구조체로 파싱해 다시 직렬화하며, 중복·알 수 없는 필드를 거부한다. 다른 구현을 만들 때는 필드 순서·문자열 이스케이프·정수 표현까지 같은 바이트를 생성해야 한다.

- 팀 신뢰 기준: `sai-mesh/manifest/1`
- 장치 등록 요청: `sai-mesh/enrollment/1`
- 승인·해제 이벤트: `sai-mesh/membership/1`

팀 ID는 관리자 공개키와 난수에, 장치 ID는 서명·암호화 공개키 쌍에 묶인다. 공개키·서명은 정해진 길이의 소문자 16진수다. 서명 검증 외에도 저차수 X25519 공개키, 잘못된 버전, 팀 불일치, 끊긴 해시 연결과 중복 요청을 거부한다.

현재 준비 버전의 한도는 승인 정보 1 MiB, 등록 요청 8 KiB, 팀당 승인·해제 이벤트 256개, 저장소당 PC 팀 32개다. 한도에 도달하면 기록을 임의로 잘라내지 않고 오류를 표시한다. 긴 이력의 체크포인트·압축은 별도 설계 후 지원한다.

## 5. 구현과 검증

- `core/src/team/mesh/identity/`: 공개 자료·서명, 키 보호 저장소, 승인 이력과 테스트.
- `core/src/secret.rs`: 새 장치 키 전용 DPAPI 함수. 기존 토큰 API와 별도 실패 정책.
- `src-tauri/src/mesh_identity.rs`: 채팅 창에서만 진입 가능한 로컬 IPC. 디스크·키 보호 작업은 별도 작업 스레드에서 실행.
- `ui-app/src/chat/settings/identity.rs`: 승인 자료 준비 화면. 가져온 팀 선택과 늦은 상태 응답 처리.

```powershell
cargo test --locked -p sai-core --target x86_64-pc-windows-msvc team::mesh::identity -- --test-threads=1
cargo check --locked -p sai-ui --target wasm32-unknown-unknown
cargo test --locked --workspace --target x86_64-pc-windows-msvc --features sai/connection-test
```

2026년 11월 15일, 이 Windows 사용자 계정에서 실제 DPAPI와 SQLite를 사용하는 신원 테스트 18개가 통과했다. 재실행 후 키 유지, 관리자 권한 분리, 등록·해제·재등록, 과거 승인 입력, 위조·다른 팀 자료, 분기 이력, 동시 승인, 저장 중 오류, 키 보호 실패·유실·손상과 공개 내보내기의 비밀키 제외를 확인했다. 서로 다른 PC와 Windows 계정 사이의 실제 등록 화면 조작은 아직 검증하지 않았다.

기존 기능을 포함한 전체 워크스페이스 테스트도 89개 통과했다. 실제 LAN 지정 테스트 1개와 외부 Firebase 테스트 3개는 일반 실행에서 제외했다. WebAssembly 검사와 릴리스 화면 빌드, 설정 화면 ID와 연결 진단 앱의 명령 분리도 확인했다.

후속 단계의 진행 상태는 [승인 장치 연결과 로컬 톡 원본](mesh-local-log.md)에 기록한다. 전체 방향은 [자동 호스트 설계](automatic-host-design.md), 단계 0 연결 진단 상태는 [PC 연결 실험](mesh-connection-experiment.md)을 따른다.
