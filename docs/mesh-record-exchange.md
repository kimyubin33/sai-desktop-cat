# 암호화된 준비 톡 교환과 상대 저장 확인

> 이전 PC 톡 통신의 기록입니다. 2026-11-17의 [새 개발 방향](development-direction.md)이 후속 개발 기준이며, 톡·PC 서버·암호문 중계의 확대는 중단합니다. 기존 코드와 사용자 자료의 실제 정리는 새 계획 1단계에서 진행합니다.

2026년 11월 16일, 승인 장치의 직접 TLS 연결에 수신 장치별 본문 암호화·양방향 기록 교환·서명된 저장 확인을 연결했다. 기존 팀 서버를 옮기는 단계와는 구분되는 준비 기능이다. 외부 조정 서비스나 추가 연결 프로그램은 사용하지 않는다. 이번 자동 검증에는 두 번째 PC가 필요하지 않다.

후속 구현으로 **다른 승인 PC가 수신자별 암호문과 최종 저장 확인을 보관·전달하는 기능**을 추가했다. 별도 중계 동의가 필요하며, 사용 흐름과 한도는 아래 8절에 정리한다.

## 1. 현재 제공하는 동작

| 항목 | 동작 |
|---|---|
| 본문 암호화 | 작성 당시 수신 목록에 있는 승인 장치마다 별도 HPKE 암호문 생성 |
| 연결 | 상호 TLS 인증·정확한 인증서 대조·장치 서명·현재 승인 이력 확인 유지 |
| 교환 동의 | 연결 확인 동의와 별도. 양쪽이 기록 교환을 허용한 서명된 연결 정보 필요 |
| 저장 확인 | 수신자가 검증·복호화하고 암호문과 확인 서명을 디스크에 커밋한 뒤 응답 |
| 발신 상태 | 원래 수신 대상 장치들의 유효한 본문 저장 확인이 모두 있어야 보관 확인 완료 |
| 재시도 | 확인이 유실되면 같은 원본 ID를 재전송. 수신 목록에 같은 메시지를 중복 추가하지 않음 |
| 기록 충돌 | 작성자가 서명한 증거로 순번 충돌이 확인되면 원본을 보존하고 교환 보류 |
| 화면 | 내 원본과 받은 본문, 대기·보류·상대 보관 확인·충돌 수 표시 |

이 절의 최초 구현은 준비 톡을 교환한다. 후속 [대화 화면의 PC 톡과 서명된 삭제 요청](mesh-automatic-connection.md#10-대화-화면의-pc-톡과-작성-장치의-삭제-요청)은 같은 경로에 v2 원본 형식과 서명된 형식 협상을 추가한다. 기존 앱의 서버 톡·Firebase UID·고정 PC 서버 기록은 자동 이전하지 않는다. 수동 모드에서는 상대의 `암호화 기록 교환`을 눌러 교환하며, [LAN 자동 발견·재연결](mesh-automatic-connection.md) 모드에서는 별도 동의 후 자동으로 처리한다. 아래 암호문 중계와 현재 인증된 연결 범위의 대표 선정까지 추가했다. 전역 단일 대표 보장과 승인 이력 자동 교환은 아직 구현하지 않았다.

## 2. 화면 흐름과 전송 범위

일반 앱의 **설정 → PC 팀 장치 등록 준비 → 내 장치와 관리자 승인 정보 → 승인 장치 연결과 암호화된 준비 톡 교환**에서 사용한다. [장치 등록과 관리자 승인](mesh-identity.md)이 먼저 필요하다.

1. 양쪽에 같은 최신 관리자 승인 이력을 등록한다.
2. 선택한 PC 팀에서 교환할 준비 톡을 작성하고 `이 PC에 저장`을 누른다. 수신 목록은 그 시점의 승인 장치 전체이며, 자기 장치도 포함한다.
3. LAN 수신 동의와 **암호화된 준비 톡 수신과 기록 교환 허용**을 양쪽에서 켜고 연결을 시작한다. 기록 교환 동의는 기본 꺼짐이다. 연결 확인만 원하면 두 번째 동의를 켜지 않는다.
4. 서명된 연결 정보를 서로 등록한다. 실행 중에는 교환 허용 여부를 바꿀 수 없고, 중지 후 새 연결 정보를 만들어야 한다.
5. 상대의 `암호화 기록 교환`을 누른다. 한 연결에서 내 발신 기록을 보낸 뒤 상대의 발신 기록을 받는다. 따라서 상대가 요청할 때도 내 전송 가능한 준비 톡이 교환될 수 있다.
6. 방향별 최대 8개 원본을 처리한다. 남은 기록이 있다고 나오면 다시 누른다. `중지`나 15분 만료로 런타임을 종료한다.

이 절차는 기능을 수동 확인할 때의 안내다. 다음 개발을 위해 사용자가 지금 두 PC 테스트를 완료해야 하는 것은 아니다.

### 보내지 않는 과거 본문

이전 v2에서 로컬 확인용으로 저장한 원본은 업그레이드 후 **이전 로컬 전용 기록 · 자동 전송 제외**로 남긴다. 키와 원본 ID는 유지하며 전송 정책을 자동으로 켜지 않는다. 새로 작성한 준비 톡에만 작성 장치가 서명한 발신 의도를 함께 저장한다. 정책의 숫자 값만 바꾸거나 다른 원본의 발신 의도 서명을 끼워 넣어도 본문을 내보내지 못한다.

새 톡도 작성 이후 관리자 승인 이력이 바뀌면 **승인 이력 변경으로 전송 보류**한다. 새 팀원에게 과거 본문을 자동 배포하거나, 해제·재승인된 키에 과거 대기 본문을 자동 재암호화하지 않는다. 기존 본문이 필요하면 내용을 확인하고 현재 수신 범위에 맞게 새 준비 톡으로 작성한다. 과거 원본의 보류를 해제하는 명령은 아직 제공하지 않는다.

순서 검증에 필요한 서명된 헤더는 본문 없이 교환할 수 있다. 여기에는 팀·장치 ID, 순번, 이전 해시, 수신 장치 ID 같은 메타데이터가 들어간다. 본문 없는 헤더의 저장 확인은 본문 전송 의무를 완료하지 않는다.

## 3. 암호화와 서명

본문은 `hpke` 0.13.0의 RFC 9180 구현으로 암호화한다. 구성은 DHKEM(X25519, HKDF-SHA256), HKDF-SHA256, ChaCha20Poly1305의 Base 모드다. 기존 장치의 별도 X25519 키를 사용하며, 전송마다 새 캡슐화 난수를 만든다. [RFC 9180](https://www.rfc-editor.org/rfc/rfc9180.html), [사용한 라이브러리 API](https://docs.rs/hpke/0.13.0/hpke/fn.single_shot_seal.html)

HPKE Base 모드 자체를 작성자 인증으로 해석하지 않는다. 원본 헤더의 Ed25519 서명에 더해, 작성 장치가 원본·수신 장치·현재 승인 이력·암호문 전체를 전송 봉투에 서명한다. 본문 암호화의 AAD에도 팀·작성자·수신자·원본 ID·승인 이력·본문 허용 여부를 묶는다. 수신자가 복호화한 버전·원본 ID·salt·본문을 원본의 서명된 해시와 대조한다.

수신 장치마다 암호문이 다르다. 다른 장치 키, 바뀐 수신자·메타데이터·암호문, 작성자 서명 오류는 거부한다. 작성 PC의 원본 본문은 DPAPI로, 수신 PC의 본문은 해당 장치용 HPKE 암호문으로 보관한다. 장치 개인키는 계속 DPAPI로 보호하며 다른 PC에 복제하지 않는다.

이 방식은 고정된 장치 복호화 키의 탈취 이전 기록에 대한 전방향 비밀성이나 발신자 익명성을 제공한다고 주장하지 않는다. 같은 Windows 사용자 권한의 악성 프로그램·운영체제 장악·수신자의 복호화 후 재공유도 방어 범위 밖이다. 자동 테스트 통과가 앱 프로토콜의 외부 보안 감사를 완료했다는 뜻은 아니다.

주요 용도 구분은 다음과 같다. 직렬화는 기존 고정 구조체·필드 순서 규약을 따른다.

| 용도 | 문자열 |
|---|---|
| 새 로컬 원본의 발신 의도 | `sai-mesh/send-intent/1` |
| HPKE 정보·AAD | `sai-mesh/body/1`, `sai-mesh/body-aad/1` |
| 전송 봉투·해시 | `sai-mesh/delivery/1`, `sai-mesh/delivery-hash/1` |
| 본문·헤더 저장 확인 | `sai-mesh/receipt/1` |
| 수신 경계 | `sai-mesh/frontier/1` |
| 기록 교환 ALPN | `sai-mesh-transfer/1` |

## 4. 저장 확인과 중단 처리

인증된 TLS 세션의 새 난수와 원본 ID·작성자·수신자·순번·전송 봉투 해시·본문 유무·승인 이력을 수신 장치가 서명한다. 수신자 DB에는 원본 헤더·암호문·저장 확인과 수신 경계를 같은 트랜잭션으로 커밋한다. 실패하거나 디스크가 가득 차면 성공 확인을 반환하지 않는다.

작성자도 확인 서명과 이번 요청의 난수·수신 대상·정확한 암호문 해시를 검증한 뒤 자기 DB에 저장한다. 이 저장이 실패하면 상대에 이미 본문이 있어도 발신 대기로 유지한다. 확인 분실 뒤의 재시도에서는 같은 원본을 다시 검증하고 새로운 요청에 맞는 확인을 발급한다. 화면의 수신 메시지는 한 번만 남는다.

발신 원본·대기 참조 행은 지우지 않고, 수신 대상별 확인으로 완료 상태를 계산한다. 원래 수신 대상이 모두 확인되기 전에는 일부 상대에게 전송한 것만으로 완료 처리하지 않는다. 다른 수신 장치가 없는 원본은 **이 PC에만 저장 · 다른 수신 장치 없음**으로 표시하고, 원격 보관 완료로 표시하지 않는다.

연결 중지·오류·시간 초과가 이미 성공한 디스크 커밋을 취소하지는 않는다. 취소 순간 실행 중인 로컬 작업 스레드가 커밋을 마칠 수 있다. 상대 확인을 받지 못한 발신 기록은 대기로 남으므로 재시도할 수 있다. 교환 결과의 확인 건수에는 재전송을 다시 확인한 경우가 포함될 수 있으며, 전체 팀의 유일 메시지 수나 전체 최신 상태를 뜻하지 않는다.

## 5. 수신 경계와 충돌

상대가 보관한 내 마지막 순번·해시를 새 난수와 함께 서명해 보낸다. 0보다 큰 순번에는 **작성자인 내가 서명한 마지막 원본 증거**도 필요하다. 상대의 주장만으로 내 장치 쓰기를 잠그지 않는다.

그 증거가 유효한데 내 로컬 원본보다 앞서 있거나 같은 순번의 해시가 다르면, 백업 복원·순번 재사용·분기 가능성으로 기록한다. 내 원본을 덮어쓰지 않고 새 쓰기와 전송을 보류한다. 수신자도 같은 작성자·순번의 다른 유효한 원본을 받으면 기존 원본을 보존하고 그 작성자의 추가 수신을 보류한다. 화면에 충돌 수를 표시한다. 자동 초기화·임의의 최신 선택·충돌 기록 지우기 명령은 없다.

다른 PC에 더 높은 기록이 없거나 모두 같은 과거 백업으로 돌아갔다면 이를 로컬 자료만으로 탐지할 수 없다. 자동 복구·키 교체·장치 백업 복원 절차는 여전히 후속 설계다. 이미 전달된 기록을 원격으로 회수하는 기능도 없다.

## 6. DB 갱신과 한도

저장 경로는 계속 `mesh/identity.sqlite3`이다. 직접 교환 단계에서 v3로 갱신했으며, 아래 중계 단계는 v4 테이블을 추가한다. v1·v2의 장치 키·관리자 키·승인 이력·서명된 로컬 원본·대기 참조를 보존한다. 기존 v2 원본은 발신 제외 상태로 초기화한다. 이전의 64 KiB 보호 데이터 한도는 긴 이스케이프 본문을 위해 128 KiB로 늘린다. 테이블 갱신과 복사는 한 트랜잭션이며, 실패하면 기존 스키마와 자료를 유지한다.

추가 테이블은 `mesh_local_send_policy`, `mesh_received`, `mesh_receive_heads`, `mesh_sent_receipts`, `mesh_transfer_blocks`다. 수신 원본·마지막 경계·저장 확인·보관 암호문의 해시가 맞지 않으면 경계를 초기화하거나 성공을 표시하지 않는다.

- 본문: UTF-8 32 KiB, 메타데이터·암호문을 포함한 프레임: 128 KiB.
- 교환: 방향별 최대 8개, 전체 최대 30초. TLS와 최초 인증 신호는 3초 제한.
- 등록 피어: 최대 8개. 인증 전 동시 수신 작업: 최대 4개.
- 로컬 원본: 팀·작성 장치별 최대 1,024개. 수신 헤더: 팀별 최대 1,024개.

한도에 도달하면 자료를 지워 공간을 만들지 않고 오류를 표시한다. 프레임 길이는 본문 할당 전에 검사한다. 공용 주소·인터넷 중계·방화벽 전체 해제·공유기 포트 자동 개방·IP 스캔은 추가하지 않았다.

## 7. 검증과 후속 작업

자동 테스트는 별도 임시 저장소·장치 키·TCP listener로 실제 Windows DPAPI·SQLite·HPKE·상호 TLS를 실행한다. 수신자별 복호화, 평문의 전송·DB 제외, 잘못된 저장 확인, 확인 분실 재시도, 수신·확인 저장 실패, 과거 본문 보류, 순번 충돌과 거짓 경계 주장 거부를 확인한다. 기존 DB 보존, 긴 본문, 양방향 실제 연결, 양쪽 동의와 카드 변조 거부, 여러 번에 나눈 교환도 검증한다.

직접 교환 단계에서는 새 테스트 19개를 포함해 전체 워크스페이스 테스트 122개가 통과했다. 이후 자동 연결과 중계 검증을 추가했다. WebAssembly 검사·릴리스 화면 빌드·화면 ID·문서 링크·진단 앱 분리도 확인한다. 실제 화면 조작 검증으로 표시하지 않는다.

```powershell
cargo test --locked --workspace --target x86_64-pc-windows-msvc --features sai/connection-test
cargo check --locked -p sai-ui --target wasm32-unknown-unknown
cargo run --locked -p xtask --target x86_64-pc-windows-msvc -- ui
```

실제 두 PC의 방화벽·공유기·절전·ARM64 네이티브 설치와 화면 조작은 배포 전 확인 항목이다. [LAN 자동 발견·대표 PC 재선정·앱 실행 수명](mesh-automatic-connection.md), 아래 암호문 중계까지 구현했다. 기존 팀 톡의 데이터 연결·명시적 이전은 후속 작업이다. 전체 방향은 [자동 호스트 설계](automatic-host-design.md)를 따른다.

## 8. 작성 PC가 꺼져 있어도 이어지는 암호문 중계

2026년 11월 16일 추가. 대표 호스트 인계에 앞서, **특정 작성 PC의 계속 접속에 의존하지 않는 기록 사본**을 구현했다. 이 단계 뒤 [현재 연결 범위의 대표 PC 선정·유지·재선정](mesh-automatic-connection.md)도 추가했으며, 전역 단일 호스트를 보장하지는 않는다. 동의한 승인 PC끼리 같은 서명 자료를 중복 없이 합치는 준비 단계다.

### 사용 흐름과 동의

1. 기존 PC 팀 준비 화면에서 최신 관리자 승인 이력을 각 PC에 등록한다.
2. LAN 수신·기록 교환·자동 연결 동의에 더해 **준비 톡의 수신자별 암호문과 저장 확인 보관·중계**를 켜고 시작한다. 동의는 실행 중 변경하지 않고 중지 후 다시 선택한다.
3. A는 현재 보낼 수 있는 원본을 각 수신 장치 키에 한 번씩 봉인하고 디스크에 보관한다. B는 자신에게 온 본문과 별도로 C에게 봉인된 사본도 보관할 수 있다.
4. A가 꺼져도 B가 가진 C용 암호문을 C에게 전달한다. B는 C용 암호문을 복호화하거나 수신 대상을 바꾸지 않는다. B 자신이 원래 수신 대상이면 별도의 B용 사본은 읽을 수 있다.
5. C가 본문을 검증·복호화하고 디스크에 저장한 뒤 서명한 저장 확인을 B가 보관한다. A가 돌아오면 이 확인을 전달한다.
6. A의 발신 대기는 원래 수신 대상들의 **실제 본문 저장 확인**이 모두 돌아와야 해제한다. B의 중계 보관 응답만으로는 해제하지 않는다.

기본값에서는 앱 재실행 시 동의나 포트를 자동 복원하지 않는다. 별도 [앱 시작·절전 복귀 자동 복구](mesh-automatic-connection.md)를 고르면 같은 Windows 네트워크·정확한 승인 이력에서만 다시 연결한다. 같은 LAN·최대 15분 실행이라는 준비 모드의 범위를 유지한다. 중지하면 새 교환은 멈추지만 이미 다른 PC에 전달한 사본이나 복호화한 본문을 회수할 수는 없다. 한 번도 다른 PC에 복사되지 않은 A의 기록은 A가 꺼져 있는 동안 전달할 수 없다. 사본을 가진 PC가 모두 꺼져 있으면 다음 접속을 기다린다.

### 검증과 저장 계약

- 중계 동의는 장기 장치 서명이 묶는 연결 정보에 포함된다. 값만 바꾼 카드는 거부한다. 양쪽 모두 중계에 동의한 경우에만 `sai-mesh-transfer/2`로 직접 교환 뒤 중계 목록을 교환한다. 한쪽만 동의하면 기존 `/1`의 직접 교환만 진행한다. 중계 필드가 없는 기존 카드는 비동의로 해석하며, 이전 앱 버전과의 중계 호환을 주장하지 않는다.
- 발견 광고는 기존 불투명 표식만 유지한다. 중계의 팀·작성 장치·수신 장치·원본 순번·암호문 크기·저장 확인 메타데이터는 인증된 승인 PC가 볼 수 있다. 네트워크 수준의 익명성을 제공하지 않는다.
- 본문은 기존 HPKE 암호문이며, 원본과 수신자·승인 이력·암호문 해시를 작성자 서명으로 검증한다. 중계 PC는 원본 서명이나 수신자의 확인을 대신 만들지 않는다. 개인키·로그인 토큰·공용 API 키·상담 원문은 중계 테이블에 넣지 않는다.
- 원본 사본과 최종 확인에는 서로 다른 보관 키를 사용한다. 최종 확인 키는 원래 암호문 해시에 묶이며, 재시도 난수 때문에 같은 확인이 계속 쌓이지 않는다. 작성 PC는 자신이 실제로 준비해 보관한 정확한 암호문에 대한 수신자 서명만 발신 완료로 반영한다.
- 중계된 최종 확인은 과거의 디스크 저장 사실이다. 전달 순간의 접속 상태나 현재 백업 상태를 보장하는 새 생존 확인으로 해석하지 않는다. 최초 직접 교환처럼 작성 PC가 방금 보낸 도전일 필요는 없지만, 서명·수신자·원본·암호문·승인 이력의 일치는 모두 검증한다.
- 누락된 앞 순번이 있으면 암호문만 보관한다. 앞 기록이 도착하면 작성자 순서로 검증하고 기존 수신 테이블에 합친다. 최종 확인 안에 든 암호문만 받은 경우도 같은 검증을 거친다. 같은 원본은 화면에 중복 추가하지 않는다.
- 동일 작성자·순번의 다른 유효한 서명 자료가 오면 원본을 덮어쓰지 않고 충돌로 보류한다. 되돌려진 작성 PC가 자기 서명 원본의 누락을 확인하면 새 저장과 전송을 잠근다. 서명 없는 상대 주장만으로 잠그지 않는다.
- 현재 승인 이력이 달라진 사본은 보관하되 자동 전달하지 않는다. 과거 승인 시점의 본문과 기존 로컬 전용 기록을 새 본문으로 다시 암호화하지 않는다. 새로 만든 현재 승인 이력의 헤더만 전달할 수 있다. 강퇴를 아직 모르는 오프라인 PC의 한계는 유지한다.

중계 단계는 `mesh/identity.sqlite3`에 `mesh_courier`를 추가해 v4로 갱신했다. 후속 앱 수명 단계는 v5의 로컬 자동 복구 동의 테이블을 추가한다. v1~v4 변환 중 기존 키·원본·발신 정책·수신 자료·충돌 기록은 유지한다. 실패하면 해당 변환을 되돌리며 알 수 없는 테이블을 교체하지 않는다. 사본과 확인에는 암호문·공개 서명 자료만 보관한다.

원본 암호문 보관을 커밋한 뒤 기존 수신 트랜잭션을 실행하며, 본문 저장 커밋 뒤에만 중계할 확인을 저장한다. 확인 저장에 실패하면 중계 성공 응답을 하지 않는다. 이미 커밋한 본문은 유지하고 다음 교환에서 확인 저장을 재시도한다. 작성 PC의 최종 확인 반영과 해당 중계 사본 보관은 같은 트랜잭션이다.

후속 v2의 삭제 이벤트는 서명된 헤더 자체에 삭제 참조를 담는다. 이 경우 본문 없는 참조의 디스크 커밋 확인도 별도로 인정하고 화면에 삭제 요청 저장 확인으로 표시한다. 일반 톡의 본문 없는 확인을 전달 완료로 바꾸지는 않는다. 자세한 의미와 구버전 교환 거부는 [PC 톡 안내](mesh-automatic-connection.md#10-대화-화면의-pc-톡과-작성-장치의-삭제-요청)를 따른다.

### 한도와 구현 위치

- 승인 장치: 나를 포함해 최대 9대. 발견·재연결 정책은 기존과 같다.
- 중계 보관: 팀별 **사본과 확인 합계 256개·직렬화 자료 합계 32 MiB**. 한 메시지도 대상 수에 따라 여러 항목을 사용한다. 자동 삭제·오래된 기록 정리 기능은 아직 없다. 한도에 닿으면 기존 자료를 유지하고 오류를 표시한다. 키·메타데이터·SQLite/WAL 파일의 실제 디스크 사용량은 직렬화 자료 합계와 다르다.
- 한 교환: 원본 암호문 준비 최대 8개, 중계 방향별 최대 8개. 남은 준비·전달이 있으면 다음 교환으로 이어진다. 프레임 128 KiB, 전체 연결 30초 제한 안에서 기존 직접 교환과 함께 수행한다.
- 목록: 최대 256개 보관 키. 중복 키와 잘못된 해시 형식을 거부한다. 원본을 새로 만드는 대신 디스크에 보관한 같은 암호문을 재전송한다.
- 검증: 같은 승인 자료의 이미 검증한 이력 상태를 호출 안에서 재사용한다. 각 이벤트·암호문·저장 확인의 서명 검증은 생략하지 않고, 다른 호출에 승인 상태 캐시를 남기지 않는다.

주요 코드는 `core/src/team/mesh/identity/courier.rs`와 `core/src/team/mesh/probe/courier.rs`다. 네이티브 명령은 `src-tauri/src/mesh_workbench.rs`, 화면 동의·상태·교환 결과는 `ui-app/src/chat/settings/workbench.rs`에 연결한다. 독립 진단 앱에 키 저장소나 중계 기능을 연결하지 않는다.

### 검증 범위와 남은 작업

Windows DPAPI·SQLite·HPKE·상호 TLS를 사용하는 별도 키·저장소의 테스트로 작성 PC 역할의 연결 종료, 중계 런타임 재시작, 늦게 켠 수신 PC와 최종 확인 복귀를 확인했다. 자동 경로 테스트는 발견 후보를 주입한 뒤 실제 인증·재연결·교환을 실행한다. 운영체제의 mDNS 발견은 이전 자동 연결 단계에서 한 PC의 실제 Wi-Fi로 별도 검증한 범위다. 변조·위조 동의·다른 암호문의 확인·순번 누락·중복·승인 변경·과거 본문 보류·커밋 실패·작성 PC 복원·v3 마이그레이션 실패도 검사했다. 여러 묶음으로 나뉜 자료의 준비와 전달을 확인했다.

중계 단계의 새 테스트 17개를 포함해 기본 워크스페이스 테스트 157개가 통과했다. 실제 LAN 지정 테스트 2개와 외부 Firebase 테스트 3개는 기본 실행에서 제외한다. WebAssembly 검사와 릴리스 화면 빌드, 화면 제어 ID·문서 링크·진단 앱 분리도 확인했다.

이 결과는 **한 PC에서 격리한 인스턴스 검증**이다. 실제 여러 PC의 방화벽·공유기·절전·배포 UI 검증과 외부 보안 검토는 완료로 표시하지 않는다. 후속 [대표 PC 우선순위·인계 상태와 앱 실행 수명](mesh-automatic-connection.md)을 추가했다. 기존 팀 톡 데이터의 연결·이전과 원격 네트워크 지원은 별도로 진행한다.
