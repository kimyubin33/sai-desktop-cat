# 3단계 첫 패치 — 앱 안의 팀 파일 목록과 전송

2026-11-17. [개발 계획](../development-direction.md)의 3단계를 시작한다. 팀 파일 목록·PC 파일 업로드·바이너리 다운로드·전송 대기·취소·재시도 경로를 연결했다. **실제 Google 계정·두 PC와 Windows 파일 선택창을 포함한 전체 흐름의 검증은 아직 남아 있다.** 정식 배포·버전 변경은 하지 않는다.

## 사용 흐름

1. 팀 카드의 **파일 보기**를 누른다. 소개 화면을 접고 선택한 팀의 파일과 전송 버튼에 집중한다. **팀 목록으로** 돌아갈 수 있다.
2. **파일 올리기**에서 Windows 선택창으로 PC 파일 하나를 고른다. 브라우저 화면이 파일 경로를 직접 지정하거나 임의 경로를 업로드하는 API는 제공하지 않는다.
3. 선택 시점의 전송용 사본을 이 PC에 보관하고 Drive에 새 파일로 보낸다. 이름이 같다고 기존 파일을 덮어쓰지 않는다. 파일·폴더 공유 권한도 별도로 확대하지 않는다.
4. **받기**에서 Windows 저장창으로 이름·위치를 고른다. 파일의 크기·변경 번호와 제공되는 체크섬을 확인한 뒤 저장한다. 기존 로컬 파일은 덮어쓰지 않으며 받은 파일을 자동 실행하지 않는다.
5. 진행 상태와 **파일 작업 취소**를 제공한다. 전송을 시작한 파일은 **전송 대기**에서 같은 사본을 다시 확인할 수 있다. **대기 사본 지우기**는 이 PC의 전송 사본만 제거하며 PC 원본·Drive 파일은 삭제하지 않는다.
6. 보이지 않는 기존 팀 파일은 **Google에서 파일 선택**으로 연결한다. 선택한 파일이 현재 팀 폴더 바로 안에 있는지 확인하며, 다른 폴더의 자료를 이동·복사·공유하지 않는다.

계정·팀을 바꾸거나 로그아웃하면 이전 파일 화면과 진행 상태를 비운다. 이전 요청의 늦은 결과는 새 화면에 반영하지 않는다. 전송 대기 항목도 계정과 대상 팀을 모두 확인한다. 대기 파일이 있는 팀은 먼저 처리하거나 사본을 지운 뒤 내 목록에서 뺄 수 있다.

## 첫 버전의 범위

- 전송 한도는 파일당 **25 MiB(26,214,400바이트)**, UI 표기는 25MB다. 계정별 전송 대기 항목은 최대 8개다. 큰 파일은 기존 Drive 폴더 화면을 이용한다.
- 팀 폴더 바로 안의 앱 접근 가능 파일을 페이지당 25개씩 읽는다. 하위 폴더 탐색·바로가기 따라가기·전체 Drive 검색은 하지 않는다.
- 기본 로그인과 팀 Drive 연결의 최소 범위를 유지한다. 파일 선택도 별도의 데스크톱 Picker에서 `drive.file`만 요청한다. 한 번에 서로 다른 파일 10개까지 허용하며 기존 계정과 Drive 사용자 ID가 같은지 확인한다.
- 폴더 선택이 모든 하위 파일의 앱 접근을 보장한다고 가정하지 않는다. 빈 결과를 ‘팀 폴더가 비었다’고 표시하지 않고 **앱에 연결된 파일**로 안내한다. 새 PC·새 사용자·다른 팀원이 추가한 파일은 실제 권한을 검증해야 한다.
- 일반 바이너리 파일의 다운로드를 지원한다. Google Docs·Sheets·Slides 등은 **Drive에서 열기**로 이용한다. PDF·Office 형식으로 내보내기와 대용량·청크 재개는 후속 범위다.
- 기존 Drive 파일 선택은 이미 팀 폴더 안에 있는 자료의 앱 접근 확인용이다. 다른 위치의 내 Drive 파일을 팀에 복사·공유하는 기능은 추가하지 않았다.
- 협업 프로젝트·업무·AI 내용 분석·Calendar 연동은 이번 패치에 포함하지 않는다.

## 전송과 원본 보존

업로드 사본과 대기 메타데이터는 로밍 설정과 다른 로컬 앱 데이터의 `google-profile-v1/file-transfers-v1/<subject hash>`에 계정별로 보관한다. 사본에는 선택한 파일 내용이 들어가므로 클라우드 성공을 확인하기 전까지 유지한다. 원본 PC 경로는 클라우드 메타데이터에 넣지 않는다. 재시도는 **선택 당시 사본**을 사용하며 바뀐 원본을 자동 재수집하지 않는다.

새 파일 ID를 Google에서 발급받아 로컬 대기에 커밋한 뒤 multipart 업로드를 시작한다. 이미 정해진 ID가 있으면 먼저 Drive에서 읽는다. 응답 유실·취소 후에는 같은 ID·생성 작업 표시·팀 부모 폴더·크기·파일 내용을 대조한다. Drive의 SHA-256이 없으면 제한된 크기로 다시 읽어 해시를 대조한다. 같은 주소의 내용이 다르면 덮어쓰지 않는다. 사본이 바뀌거나 손상됐을 때도 새 업로드를 진행하지 않는다.

이 방식은 같은 전송 작업의 재시도에서 중복 파일을 막는다. 사용자가 원본을 새로 선택해 별도 업로드를 시작하면 새 작업·새 파일이며, 같은 이름의 파일이 여러 개 존재할 수 있다. 중단된 multipart 전송은 바이트 위치부터 재개하지 않고 같은 파일 ID를 확인한 뒤 처음부터 재전송한다. 원격 요청이 이미 서버에 도달했다면 취소 뒤 Google에서 저장이 끝날 수도 있으며, 대기 항목 재시도에서 결과를 확인한다.

다운로드는 고정된 Google API 주소에서만 받고 리디렉션을 자동으로 따라가지 않는다. 크기·응답 시간·본문 크기를 제한하며 다운로드 제한이나 악성 파일 차단을 우회하는 옵션을 켜지 않는다. 파일 및 팀 접근을 다시 확인하고, 받는 중 버전·크기·체크섬이 달라졌다면 최종 파일로 저장하지 않는다.

Windows 저장은 사용자가 고른 폴더 안에 임시 파일을 완전히 쓴 뒤, **기존 파일 교체 옵션 없이** 최종 이름으로 이동한다. 다운로드 도중 같은 이름의 파일이 생겨도 보존한다. Drive 이름의 경로 문자·Windows 장치 이름·지나치게 긴 이름은 저장창의 기본 이름을 안전하게 만드는 데만 정리하며 Drive 원본 이름은 바꾸지 않는다.

앱 종료·전원 중단 때는 일부 임시 파일이 남을 수 있다. 사본을 지웠으나 대기 메타데이터 커밋이 실패한 경우에도, 이미 저장된 Drive 내용이 일치하면 다음 확인에서 완료할 수 있다. 업로드 성공을 확인한 뒤에만 대기 사본을 정리한다. 사용자 원본 파일은 자동 삭제하지 않는다.

## 검증

자동 검사 전체 **115개 통과**: 핵심 109개, 네이티브 4개, UI 공통 2개. 기존 Firebase 실서비스 검사 3개는 실행 제외했다. Wasm UI와 x64 Windows 빌드를 확인했다. 이번에 추가한 15개 검사는 다음을 포함한다.

- 비 UTF-8 바이너리 바이트 그대로 업로드·검사, 0바이트 파일 처리, 전송 대기 8개 제한.
- 업로드 성공 후 오류 응답·앱 재시작·로컬 사본 누락에서도 같은 ID와 생성 1회 확인.
- 손상된 사본·다른 내용의 원격 ID를 덮어쓰지 않음, 손상된 로컬 대기 파일을 읽기 실패로 보호.
- 공유 해제·읽기 전용 팀에서 업로드 거절, 원격 접근이 끊겨도 내 대기 사본 제거 가능.
- 전송 중 취소 및 로그아웃, 다른 계정에서 이전 계정 대기 항목 처리 거절, 선택한 팀과 다른 대기 작업 거절.
- 다른 폴더 파일·Google 문서의 바이너리 다운로드 거절, 버전 변경·해시 불일치·잘린 응답·과대 응답·외부 리디렉션 거절.
- 불완전한 목록을 정상적인 빈 폴더로 취급하지 않음, 파일 선택 10개 제한·중복/경로 문자열 거절.
- Windows 최종 저장에서 기존 파일 및 저장 직전 생긴 동일 이름 파일을 덮어쓰지 않음.

화면은 실제 인증을 우회한 네이티브 빌드가 아니라, **별도의 로컬 웹 미리보기**에서 가상 자료와 실제 빌드한 Wasm UI를 사용해 확인했다. 팀 → 파일 중심 화면, 일반 파일의 받기 버튼, Google 문서의 Drive 열기, 전송 대기, 가상 진행 이벤트 → 재시도 완료 후 대기 제거를 확인했다. 이 과정에서 큰 소개 영역이 파일 목록을 가리는 문제를 고쳐, 파일 화면에서는 소개 영역을 접도록 했다. 검증 도우미와 가상 로그인 정보는 Git 제외 `target/`에만 있으며 제품 코드에 로그인 우회는 추가하지 않았다. 검증 창과 127.0.0.1 도우미는 종료했다.

이 검사는 **실제 Google 동의·API 활성화·파일 접근 상속·파일 선택창·메일 배달·두 계정·두 PC의 전체 동작**을 대신하지 않는다. 실제 Google 토큰·개인 파일은 테스트에 복사하거나 전송하지 않았다. 전체 Drive 권한으로 조용히 확대하지 않으며, 2·3단계 완료 및 정식 배포 전에 실제 권한·전송·취소·설치 검증을 마쳐야 한다.

다음 작업은 최소 권한의 실제 파일 흐름 확인과 **협업 칸의 프로젝트·할 일 저장 구조**다. 팀 AI와 Calendar는 확정된 후속 단계를 따른다.

## 공식 근거

- [Drive 권한 범위](https://developers.google.com/workspace/drive/api/guides/api-specific-auth): 앱에서 만들거나 선택한 자료의 최소 접근 범위를 사용한다.
- [데스크톱 Picker](https://developers.google.com/workspace/drive/picker/guides/desktop-mobile-picker): 브라우저 선택·`drive.file` 단독 흐름을 유지한다.
- [Drive 업로드](https://developers.google.com/workspace/drive/api/guides/manage-uploads): 사전 발급 ID로 불명확한 저장 결과를 재확인한다.
- [파일 메타데이터](https://developers.google.com/workspace/drive/api/reference/rest/v3/files): 부모·버전·크기·제공되는 체크섬과 현재 기능을 확인한다.
- [Drive 다운로드와 내보내기](https://developers.google.com/workspace/drive/api/guides/manage-downloads): 바이너리 다운로드와 Google 문서 내보내기를 구분한다.
- [Windows 파일 선택](https://learn.microsoft.com/en-us/windows/win32/api/commdlg/nf-commdlg-getopenfilenamew): 앱의 선택창에서 사용자가 파일 경로를 고른다.
