# 승인 PC의 LAN 자동 발견과 재연결

2026년 11월 16일, [암호화된 준비 톡 교환](mesh-record-exchange.md)에 자동 발견·연결 정보 갱신·대기 기록의 자동 교환을 추가했다. 같은 LAN에서 동의한 실행 동안 동작하며 외부 조정 서비스나 별도 연결 프로그램을 설치하지 않는다.

## 1. 구현 범위

| 항목 | 동작 |
|---|---|
| 자동 발견 | 선택한 LAN에서 현재 승인된 장치 쌍만 해석하는 임시 표식 광고 |
| 연결 정보 교환 | 새 서버·클라이언트 도전, 장치 서명과 HPKE 암호화로 양쪽의 연결 정보 확인 |
| 재연결 | 상대 앱의 새 실행·인증서를 검증하고 이전 연결 정보를 교체 |
| 대기 기록 | 기존 상호 TLS·본문 암호화·서명된 저장 확인 경로로 양방향 교환 |
| 여러 묶음 | 방향별 8개를 처리한 뒤 남은 기록을 이어서 자동 교환 |
| 실패 | 대기 원본 유지. 재시도 간격을 늘리고 다른 장치도 순서대로 처리 |
| 중지 | 버튼·15분 만료·장치 승인 변경·내 원본 충돌 시 접속 정리 |
| 화면 | 자동 찾기·장치 정보 확인·교환·재시도 상태와 새 수신 기록 표시 |

현재는 **실행 중인 준비 기능**이다. 기본값에서는 앱 재실행 시 동의를 복원하거나 LAN 포트를 열지 않는다. 아래 8절의 별도 자동 복구를 선택한 경우에만 저장한 팀·승인 이력·Windows 네트워크를 확인해 다시 연결한다. [수신자별 암호문 중계·복제](mesh-record-exchange.md)와 아래 7절의 **현재 인증된 연결 범위에서 대표 PC 선정·재선정**, 9절의 **기존 공개 톡을 선택한 PC 전용 보관**도 제공한다. 기존 팀 톡 화면의 실제 서버 전환과 서로 다른 네트워크의 자동 연결은 후속 단계다. 일반 팀원 PC가 연결을 맡아도 관리자 승인 권한을 얻지 않는다.

## 2. 사용 흐름

일반 앱의 **설정 → PC 팀 장치 등록 준비 → 내 장치와 관리자 승인 정보 → 승인 장치 연결과 암호화된 준비 톡 교환**에서 사용한다.

1. 관리자가 승인한 각 PC에 같은 최신 승인 이력을 등록한다.
2. PC 팀과 이 PC의 LAN 주소를 선택한다.
3. LAN 수신, 암호화 기록 교환, **같은 LAN의 승인된 PC 자동 찾기·재연결·대기 기록 교환**을 모두 켠 뒤 시작한다. 자동 연결은 양쪽이 켜야 한다.
4. 같은 LAN의 상대가 발견되면 서명된 연결 정보를 복사·붙여넣기하지 않아도 확인과 기록 교환이 진행된다.
5. 새 준비 톡을 저장하면 기존 발신 대기를 처리한다. 상대에서 작성한 기록도 자동 교환 때 받으며 화면을 주기적으로 갱신한다.
6. `중지` 또는 15분 만료로 종료한다. 실행 중 동의·주소는 변경하지 않고, 중지 후 다시 선택한다.

자동 연결에 동의하지 않은 상대에게는 수동 기록 교환 권한만으로 자동 전송하지 않는다. 기존 수동 등록·확인·교환 기능은 유지한다. 다른 승인 장치가 없으면 발견 광고를 내보내지 않는다. 이번 버전은 다른 활성 승인 장치 최대 8대까지 지원하며, 초과하면 일부를 임의로 제외하지 않고 자동 시작을 거부한다.

이 안내는 수동 확인이 필요할 때의 절차다. 사용자가 지금 두 번째 PC 테스트를 완료해야 다음 개발을 진행할 수 있는 것은 아니다.

## 3. 발견 광고와 신뢰 확인

발견 서비스는 `_sai-sync._tcp.local.`이다. 선택한 IPv4 인터페이스에서 실행 ID, 프로토콜 버전, 장치 쌍별 불투명 표식과 접속 주소만 광고한다. 팀 이름·팀 ID·장치 ID·인증서·로그인 토큰·본문을 광고에 넣지 않는다. 앱 사용 사실, 주소·포트, 표식 수 같은 트래픽 정보까지 숨기지는 않는다.

승인된 두 장치의 X25519 공유 값에서 팀·승인 이력·정렬한 두 장치 ID에 묶인 HKDF-SHA256 키를 만든다. 이를 사용한 HMAC-SHA256 표식은 광고 실행 ID와 발신·수신 장치에 묶인다. 새 실행이나 승인 이력에서는 다른 표식이 된다. 제3의 팀원도 자기 장치 쌍의 키로 다른 두 장치의 표식을 해석하지 못한다. 키 유도와 MAC에는 기존 `ring` 구현을 사용한다. [HKDF 규약](https://www.rfc-editor.org/rfc/rfc5869.html), [HMAC 규약](https://www.rfc-editor.org/rfc/rfc2104.html)

표식이 맞는 광고도 연결 후보일 뿐이다. 복사한 광고만으로 상대 인증서나 장치 권한을 등록하지 않는다. 광고가 같은 승인 장치의 것인지 확인하고, 선택한 서브넷의 사설 IPv4 유니캐스트 주소·포트만 시도한다. 발신 소켓도 선택한 로컬 주소에 묶는다. 네트워크 검색은 없으며, 광고에 나온 제한된 후보만 사용한다.

### 최초 연결 정보 교환

서로의 새 TLS 인증서를 아직 모르는 단계에는 작은 별도 연결 정보 교환을 사용한다.

1. 후보의 주소로 접속해 불투명 표식과 클라이언트 난수를 보낸다.
2. 수신 PC가 해당 표식을 확인하고 연결마다 새 서버 난수를 보낸다.
3. 발신 PC는 두 난수·대상 실행·표식·양쪽 장치·현재 승인 이력·자기 연결 정보를 장치 키로 서명하고, 수신 장치용 HPKE 암호문으로 보낸다.
4. 수신 PC는 현재 승인·서명·새 도전·자동 교환 동의·실제 접속 IP를 확인한다. 자기 연결 정보도 같은 도전에 서명해 발신 장치용 암호문으로 돌려준다.
5. 양쪽이 새 증명을 검증한 뒤 연결 정보를 등록한다. 같은 장치의 이전 실행 정보는 이 경로를 통과한 후에 교체한다.

이 단계의 TCP에는 공개 난수·임시 표식과 암호화된 연결 정보만 흐른다. 팀 기록 API나 원격 명령 실행 기능은 없다. 이후 **실제 기록은 기존 TLS 1.3 상호 인증·정확한 인증서 대조·수신 장치별 본문 암호화 경로로만 교환**한다. TLS 인증서 검증을 생략하는 설정을 추가하지 않았다.

캡처한 이전 요청은 새 서버 도전에 답할 수 없고, 이전 응답도 새 클라이언트 난수와 맞지 않는다. HPKE Base 모드만으로 작성자를 신뢰하지 않고 장치 서명도 검증한다. 자동 동의 값은 서명된 연결 정보에 포함하므로 카드의 숫자·불리언 값만 바꿔 수동 동의를 자동 동의로 올릴 수 없다.

| 용도 | 구분 값 |
|---|---|
| 발견 키·표식 | `sai-mesh/auto-route/1`, `sai-mesh/auto-tag/1` |
| 연결 정보 암호화·AAD | `sai-mesh/auto-bootstrap/1`, `sai-mesh/auto-aad/1` |
| 새 도전의 요청·응답 서명 | `sai-mesh/auto-request/1`, `sai-mesh/auto-reply/1` |
| 초기 식별자 | `SAIAUTO1` |

## 4. 재시도와 기록 교환

장치 쌍마다 안정적인 장치 ID 순서로 한쪽이 정기 교환을 시작해 양쪽의 중복 연결을 줄인다. 이 역할은 운영 관리자나 전역 대표 서버 선출이 아니다. 정상이면 약 5초 간격으로 확인하고, 기록이 남으면 다음 묶음을 이어서 처리한다. 로컬 저장은 자동 작업을 깨우되, 실패한 접속의 대기 간격을 초기화하지 않는다.

실패 시 약 1·2·4·8초 순으로 작은 무작위 지연을 더해 최대 30초까지 간격을 늘린다. 같은 광고를 반복 입력해도 실패 횟수나 재시도 시각을 초기화하지 않는다. 여러 상대는 순환해서 처리하며, 한 번에 한 발신 작업만 수행한다. 끊김·시간 초과는 전송 완료가 아니므로 확인받지 못한 원본은 대기로 남는다.

상대 앱이 재실행되어 인증서·실행 ID·포트가 바뀌면 새로운 발견과 도전을 거쳐 갱신한다. 재시도와 재접속에서 원본 ID·장치 순번·수신 경계는 유지한다. 받은 원본을 중복 추가하거나 원본을 새 서버 자료로 임의 복사하지 않는다.

이전 로컬 전용 기록과 승인 이력이 달라진 과거 본문을 보내지 않는 규칙은 그대로다. 자동 연결이 이 보류를 해제하지 않는다. 관리자 승인 이력이 바뀌거나 키를 열지 못하면 자동 실행을 닫고 화면에 이유를 표시한다. 내 원본의 충돌도 자동 실행을 보류하며, 기존 원본을 초기화하지 않는다.

## 5. 제한과 종료

- 같은 서브넷의 사설 IPv4 LAN만 지원한다. 게스트 네트워크의 장치 격리나 멀티캐스트 차단에서는 수동 연결이 필요할 수 있다.
- 내 로컬 IP 주소 자체가 달라졌다면 새 주소를 선택해 다시 시작한다. 잠깐의 단절 뒤 같은 주소로 돌아온 경우는 재시도한다.
- 다른 활성 승인 장치·발견 후보는 최대 8대다. 광고 태그는 최대 8개, 후보 주소는 최대 4개다.
- 최초 교환 프레임은 할당 전 16 KiB 한도를 검사한다. 연결 정보 교환은 8초 제한이며, 서명·복호화 작업의 동시 수신은 1개로 제한한다.
- 기록 교환의 방향별 8개·전체 30초·인증 전 수신 작업 4개·기록 한도는 기존 규칙을 유지한다.
- 중지·만료·승인 변경 때 광고·작업·listener를 정리한다. 이미 진행 중인 로컬 작업 스레드의 커밋을 취소했다고 주장하지 않으며, 확인받지 못한 원본은 재시도한다.

자동 발견 자체는 DB 스키마를 추가하지 않는다. 중계 단계는 v4 테이블, 아래 자동 복구 단계는 v5의 동의 테이블을 추가한다. 새로운 개인키·토큰을 외부에 저장하지 않는다. 발견용 파생 키는 실행 중 메모리에만 보관하고 소유 버퍼를 해제할 때 지운다. 기존 장기 장치 키의 보호·복구 한계와 프로토콜의 외부 보안 검토 미완료 상태는 유지한다.

## 6. 구현과 검증

- `core/src/team/mesh/identity/automatic.rs`: 발견 키, 현재 승인 확인, 도전에 묶인 서명·암호화.
- `core/src/team/mesh/probe/auto.rs`: 연결 정보 교환, 재시도, 작업 수명과 상태.
- `core/src/team/mesh/probe/auto_discovery.rs`: 선택한 인터페이스의 mDNS 광고·발견.
- `src-tauri/src/mesh_workbench.rs`, `ui-app/src/chat/settings/workbench.rs`: 별도 동의, 새 저장 알림, 실행 상태와 수신 화면 갱신.

발신 의도 검증에서는 같은 DB 스냅샷의 관리자 서명으로 검증된 공개키와 대조해 중복 키 검증을 줄였다. 각 원본의 발신 의도 서명 검증은 유지한다. 수신 저장과 발신 확인 저장이 모두 끝난 시점을 자동 교환 완료 테스트의 기준으로 삼는다.

기본 워크스페이스 테스트 140개가 통과했다. 실제 LAN 지정 테스트 2개와 외부 Firebase 테스트 3개는 기본 실행에서 제외한다. 새 검증에는 장치 쌍·실행별 표식 분리, 새 도전 재사용 거부, 자동 동의 변조 거부, 선택 서브넷 제한, 수동 등록 없는 양방향 교환, 재실행 후 인증서 갱신, 과거 광고 입력, 여러 묶음의 자동 처리, 중지·만료·승인 변경·충돌 시 접속 정리가 포함된다.

한 PC의 실제 Wi-Fi에서 **서로 다른 키·저장소를 가진 두 인스턴스**가 mDNS로 발견하고 암호화 기록·상대 저장 확인을 교환하는 별도 테스트도 통과했다. 네트워크 제한 환경에서는 발견 후보가 없었고, 같은 코드를 LAN 통신이 허용된 환경에서 실행해 확인했다. 방화벽이나 공유기 설정을 자동 변경하지 않았다.

```powershell
cargo test --locked --workspace --target x86_64-pc-windows-msvc --features sai/connection-test
cargo check --locked -p sai-ui --target wasm32-unknown-unknown
cargo run --locked -p xtask --target x86_64-pc-windows-msvc -- ui

# 실제 인터페이스 확인은 LAN 통신이 허용된 환경에서 별도로 실행
$env:SAI_MESH_AUTO_LAN_TEST = '이-PC의-사설-IPv4-주소'
cargo test --locked -p sai-core --target x86_64-pc-windows-msvc team::mesh::probe::auto::tests::windows::approved_devices_discover_and_exchange_on_the_selected_real_lan -- --ignored --exact --nocapture
```

실제 두 PC 사이의 방화벽·공유기·절전·ARM64 네이티브 설치와 화면 조작은 배포 전 확인 항목으로 남는다. 이번 결과를 서로 다른 PC나 외부 네트워크의 검증 완료로 표시하지 않는다. [수신자별 암호문 복제](mesh-record-exchange.md), 아래 대표 재선정과 앱 실행 수명 통합을 연결했으며, 기존 팀 톡은 후속 단계에서 명시적으로 이전한다. 전체 방향은 [자동 호스트 설계](automatic-host-design.md)를 따른다.

## 7. 현재 연결 범위의 대표 PC와 역할 인계

2026년 11월 16일 추가. 대표는 **기록 교환을 우선하는 중계 역할**이다. 원본·장치 개인키·관리자 권한·팀 저장 경로를 대표 PC에 종속시키지 않는다. PC마다 최근 확인한 연결이 다를 수 있으며, 전 세계에 한 대뿐인 서버를 보장하는 합의나 배타 쓰기 잠금은 추가하지 않았다.

### 사용과 후보 조건

준비 화면의 **암호문 중계와 대표 PC 후보 참여**에 동의하고 자동 연결을 시작한다. 이전 중계 동의와 같은 실행 범위이며, 실행 중 변경할 수 없고 최대 15분 뒤 종료한다. 동의하지 않은 PC는 대표 후보가 되지 않는다. 수동 기록 교환과 자동 직접 교환은 그대로 사용할 수 있다.

장기 장치 서명이 연결 카드의 `host` 지원·참여 값까지 묶는다. 이 값이 없거나 거짓인 카드는 후보에서 제외하며, 값을 바꿔 위조하면 서명 검증에 실패한다. 후보는 같은 최신 승인 이력의 활성 장치이고 자동 연결·기록 교환·중계에도 동의해야 한다. 발견 광고만 받았거나 카드만 등록한 상태로는 다른 PC를 대표로 선정하지 않는다.

상대마다 `sai-mesh-host/1`의 별도 상호 TLS 연결에서 선택한 단일 LAN 주소·정확한 인증서·현재 장치 승인·새 난수 응답을 확인한다. 응답 전후 현재 등록된 카드·주소·서명과 일치해야 하며, 이전 실행에서 늦게 돌아온 응답은 새 실행에 합치지 않는다. 원래 기록 교환의 30초 작업이나 발신 작업 잠금과 별도로 후보를 확인한다. 새로운 발견 서비스나 공개 광고 필드는 추가하지 않는다.

같은 장치 ID의 연결 카드가 여러 개 남으면 어느 쪽이 최신인지 임의로 고르거나 후보 수를 늘리지 않는다. 해당 장치는 후보에서 제외한다. 새 도전에 응답하는 기존 자동 연결 경로가 최신 실행을 검증하고 이전 카드를 교체하면 다시 확인한다. 이전 앱과의 전체 호환은 검증 완료로 표시하지 않으며, 같은 새 버전의 준비 모드를 대상으로 한다.

### 선정과 재선정 규칙

| 항목 | 현재 값과 의미 |
|---|---|
| 초기 탐색·후보 안정 시간 | 2초. 처음 켠 PC의 벽시계 시각을 비교하지 않는다. |
| 우선순위 | 안정 시간이 지난 후보 중 장기 장치 ID의 오름차순. 자신도 실행·승인·동의가 유효한 로컬 후보다. |
| 대표 유지 시간 | 살아 있는 현재 대표를 최소 10초 유지한 뒤 더 높은 우선순위의 안정된 후보로 조정한다. |
| 응답 재확인 | 후보별 완료 후 약 5초 뒤 다시 확인. 최대 2개를 동시에 처리한다. |
| 확인 요청 제한 | 연결·인증·응답 전체 5초. 한 PC의 대기로 다른 후보 확인을 모두 멈추지 않는다. |
| 최근 응답 유효 시간 | 마지막 성공 응답부터 15초. 실패나 광고는 갱신하지 않는다. |
| 대표 응답 만료 | 최소 유지 시간과 무관하게 다음 안정된 후보를 고른다. 자신밖에 없으면 `현재 확인한 후보는 이 PC뿐`으로 표시한다. |
| 앱 재실행·인증서 변경 | 과거 실행의 응답을 이어 쓰지 않고 새 카드와 실제 응답을 확인한다. |

이 시간은 로컬 단조 시계(`Instant`)로 측정한다. PC 날짜 변경이나 상대가 보낸 시각으로 대표 순서를 정하지 않는다. 15초는 최근 응답을 사용하는 범위이며 엄격한 전환 완료 시간 보장은 아니다. 운영체제 스케줄링, CPU·저장소 지연, 새로운 후보의 인증과 안정 시간에 따라 실제 표시가 늦을 수 있다. 응답이 만료되면 상태 조회도 그 상대를 유효한 대표로 계속 보여 주지 않는다.

네트워크가 둘로 나뉘면 각 PC의 직접 확인 범위에서 서로 다른 대표를 고를 수 있다. 서로 다시 인증한 뒤 안정 시간·유지 규칙을 적용하면 같은 후보 집합에서는 같은 장치 ID로 수렴한다. 다른 PC가 주장하는 대표나 최초 실행 시각을 믿어 권한을 주는 프로토콜은 없다. 현재 보이는 PC를 투표 정족수로 해석하지 않는다.

### 교환과 중지에 미치는 영향

대표와 연결된 교환은 기존 약 5초 주기, 대표가 별도로 있는 PC끼리의 보조 교환은 약 15초 주기를 사용한다. 장치 쌍의 발신 담당은 기존의 작은 장치 ID 규칙을 유지한다. 대표 연결이 발신 가능한 경우 우선 기회를 주되, 연속 우선 처리 때문에 다른 장치가 밀리지 않도록 기존 순환 처리와 번갈아 적용한다. 남은 묶음은 다음 틱에 이어서 처리한다.

대표 변경 시 건강한 연결의 대기 작업을 깨워 새 역할에 맞게 교환을 시도한다. 실패한 연결의 재시도 간격은 초기화하지 않는다. 새 준비 톡 저장도 기존처럼 건강한 연결을 깨운다. 보조 연결과 각 PC의 로컬 작성은 계속 유지하므로, 대표 변경을 기다려야 새 톡을 로컬에 저장할 수 있는 구조는 아니다.

대표 변경은 보관된 사본을 새 서버 DB로 복사하는 작업이 아니다. 이미 가지고 있는 수신자별 암호문을 기존 중계 경로로 이어 보내며, 최종 수신자의 서명된 디스크 저장 확인만 발신 완료로 반영한다. 사본이 없는 PC의 기록이나 꺼진 PC에만 있는 기록을 만들어 내지 않는다. 전체 기록이 최신이라는 상태도 추가하지 않는다.

중지·만료·앱 종료 시 후보 확인 작업과 소켓을 정리한다. 승인 이력 변경·자기 장치 강퇴·자기 원본 충돌·키 확인 실패는 기존 자동 연결과 함께 종료한다. 장기 키·관리자 승인·원본 로그·충돌 기록은 바꾸지 않는다. 후보·대표 상태는 메모리에만 보관한다. 아래 v5 테이블은 대표 상태가 아닌 로컬 자동 복구 동의용이다.

### 구현과 검증

`core/src/team/mesh/probe/host.rs`에 단조 시계 기반 선정과 제한된 동시 후보 확인을 구현했다. `probe/auto.rs`는 대표 우선순위와 보조 주기를 적용하고, `probe/approved.rs`와 `probe/mod.rs`는 서명된 참여 값·상호 TLS 경로·수명을 연결한다. 준비 화면은 현재 후보 수, 이 PC의 역할, 확인한 대표 ID, 응답 유효 시간과 일부 후보의 오류를 표시한다.

새 테스트 14개는 초기 안정 시간·ID 순서·대표 유지·응답 만료·실행 교체·분리 후 수렴·보조 교환 유지와 실제 TLS 연결을 확인한다. 실제 연결에서는 3개 장치의 대표 수렴과 종료 후 재선정, 위조 참여 값 거부, 후보 중복 제외, 새 인증서 확인, 강퇴 후 중지, 응답 대기 중 취소를 검사했다. 작성 대표가 종료된 뒤 새 대표가 늦게 켠 수신자에게 암호문을 전달하고, 작성자가 돌아왔을 때 최종 확인을 돌려주는 경로도 검증했다.

기본 워크스페이스 테스트 **171개가 통과**했다. 실제 LAN 지정 테스트 2개와 외부 Firebase 테스트 3개는 기본 실행에서 제외한다. 전체 동시 검사에서는 큰 기록 묶음의 30초 제한에 도달할 수 있어, 해당 묶음 테스트는 시간 제한 오류만 다음 시도로 이어서 확인하도록 보완했다. 다른 오류는 실패로 처리하며, 최종 수신 개수와 중복 없는 저장·묶음 한도는 그대로 검사한다. 실제 연결의 시간 제한은 늘리지 않았다. WebAssembly 검사·릴리스 화면 빌드·화면 제어 ID·문서 링크·독립 진단 앱 분리도 확인했다.

선정 규칙의 시간 테스트는 로컬 단조 시계를 진행시켜 확인한다. 연결 테스트는 **한 PC의 별도 키·저장소와 실제 TCP·DPAPI·HPKE·상호 TLS**를 사용하며, 재연결 일부에서는 발견 후보를 주입한다. 실제 여러 PC의 네트워크 분리·방화벽·절전·설치 UI나 외부 보안 검토를 완료한 결과는 아니다. 아래에 앱 실행 수명·재시작 동의·절전 복귀를 추가했으며, 기존 팀 톡의 실제 이전은 후속 단계다.

## 8. 앱 시작·종료와 절전 복귀

별도의 **이 팀과 Windows 네트워크를 기억하고 자동 연결** 선택을 추가했다. 기본값은 꺼짐이며, 선택하지 않은 기존 동의를 앱 재실행이나 절전 복귀 때 재사용하지 않는다. 현재는 **한 PC에서 선택한 PC 팀 하나**의 자동 연결 또는 중계·대표 후보 모드만 저장한다. Windows 로그인으로 사이가 자동 실행되는 경우도 앱 시작에 포함된다.

### 자동 복구를 선택했을 때

1. 준비 화면에서 팀·LAN 주소·기록 교환·자동 연결을 고르고, 필요하면 중계·대표 후보 참여를 선택한다.
2. 자동 복구를 추가로 선택하고 시작한다. 자동 복구는 Windows가 개인 또는 도메인 네트워크로 분류한 연결에서만 저장한다. 앱은 네트워크 종류나 방화벽 설정을 변경하지 않는다.
3. 다음 앱 시작에는 저장한 동의의 장치 서명, 장치 키, 팀과 정확한 승인 이력을 확인한다. 새 장치나 키를 자동 생성하지 않는다.
4. 같은 Windows 네트워크·어댑터·서브넷과 네트워크 종류가 확인되면 새 인증서·실행 ID·포트로 연결한다. 이전 수동 카드·대표의 생존 확인은 재사용하지 않는다.
5. 절전·앱 종료는 동기 취소 신호로 새 작업을 막고 수신·교환·대표 확인 작업을 정리한다. 앱 종료 뒤에는 다른 프로그램이나 Windows 서비스가 서버를 계속 실행하지 않는다.
6. 절전 복귀나 일시적인 링크 복구는 **현재 실행에 남은 시간**으로만 다시 연결한다. 원본과 수신 기록·암호문 사본·저장 확인은 유지하며, 기존 전송 경계에서 재시도한다.

동의하지 않은 일회성 실행은 절전이나 실행 중단 후 다시 시작해야 한다. 연결 확인만 하는 모드와 수동 기록 교환 모드에는 저장한 자동 복구를 허용하지 않는다.

### 시간과 종료 정책

| 상황 | 동작 |
|---|---|
| 동의 없는 첫 실행 | 키·팀·포트·자동 복구 설정을 만들지 않음 |
| 유효한 자동 복구 동의로 앱 시작 | 해당 앱 실행에 새 15분 예산 부여 |
| 절전·링크 중단·주소 변경 | 원래 예산 유지. 복구 때 15분으로 초기화하지 않음 |
| 15분 만료 | 현재 실행 종료. 같은 앱 실행에서 자동 갱신하지 않음 |
| 만료 뒤 새 앱 실행 | 저장된 자동 시작 동의가 여전히 유효하면 새 15분 실행 가능 |
| `중지·자동 복구 해제` | 현재 연결 중지와 다음 앱 시작 동의 삭제. 새 시작 요청과 겹쳐도 늦은 시작 결과를 채택하지 않음 |
| 저장 동의 해제 실패 | 현재 연결은 중지하고 저장 실패를 알림. 저장된 동의가 남을 수 있으므로 성공으로 표시하지 않음 |
| 승인 변경·강퇴·키 확인 실패·원본 충돌 | 자동 복구 보류. 새 승인을 자동 동의로 바꾸지 않고 다시 선택 필요 |
| 창만 닫기 | 기존처럼 앱은 트레이에 남음. 앱의 명시적 종료와 구분 |

사용 시간은 Windows 부팅 이후의 `GetTickCount64`로 계산해 PC 날짜를 바꾸거나 절전 복귀하면서 예산을 늘리지 않도록 한다. 전원 알림을 놓치거나 앱 실행 간격이 10초 넘게 벌어져도 감독 작업이 기존 실행을 정리하고 남은 예산·동의·네트워크를 다시 확인한다. 감독 작업은 약 1초 주기이며 네트워크 대기 중에는 약 5초 간격으로 확인한다. 실제 운영체제 정리 시각의 실시간 보장은 아니다. [GetTickCount64](https://learn.microsoft.com/en-us/windows/win32/api/sysinfoapi/nf-sysinfoapi-gettickcount64)

Windows `PowerRegisterSuspendResumeNotification`으로 절전·복귀 알림을 받는다. 콜백에서는 DB 작업이나 새 연결을 실행하지 않고 취소·복귀 신호만 전달한다. 연이어 오는 복귀 알림은 한 번의 복구로 처리하며, 종료 신호 뒤에는 복귀 신호가 연결을 다시 열지 못한다. 알림 등록에 실패하면 실행 간격 감지가 보조 경로가 된다. [전원 알림 API](https://learn.microsoft.com/en-us/windows/win32/api/powerbase/nf-powerbase-powerregistersuspendresumenotification)

### 동의한 네트워크의 범위

Windows Network List Manager에서 연결 중인 어댑터 GUID, 네트워크 GUID와 개인·공용·도메인 종류를 읽고, 선택한 IPv4의 서브넷·마스크를 함께 묶는다. 단순히 `192.168.x.x` 주소가 같다는 이유로 다른 네트워크에 자동 연결하지 않는다. 프로필 분류는 자동 복구 범위를 정하는 입력이며, 방화벽에서 통신이 허용됐다는 의미가 아니다. [네트워크 ID](https://learn.microsoft.com/en-us/windows/win32/api/netlistmgr/nf-netlistmgr-inetwork-getnetworkid), [네트워크 분류](https://learn.microsoft.com/en-us/windows/win32/api/netlistmgr/nf-netlistmgr-inetwork-getcategory)

같은 네트워크·어댑터·서브넷에서 DHCP 주소만 바뀌면 현재의 단일 사설 IPv4를 골라 새 연결을 연다. 인터페이스가 없거나 주소가 여러 개로 모호하거나 프로필을 확인할 수 없으면 포트를 열지 않고 기다린다. 다른 프로필·어댑터·서브넷으로 이동하거나 네트워크가 공용으로 바뀌어도 원래 동의한 범위가 돌아오기 전까지 기다린다. 현재 실행의 예산이 끝나면 대기도 종료한다. 새 범위를 사용하려면 사용자가 주소와 동의를 다시 선택한다.

네트워크 확인은 주기적인 OS 조회이며 패킷 방화벽을 대신하지 않는다. 네트워크 변경의 감지와 정리 사이에 스케줄링 지연이 있을 수 있고, OS 프로필 자체를 공격자에게서 인증하는 새 규약을 만든 것은 아니다. 실제 기록 교환은 여전히 관리자 승인·장치 서명·상호 TLS·수신자별 암호화로 제한한다. 외부 조정 서버, 공유기 포트 개방, IP 스캔, 별도 VPN 프로그램을 추가하지 않는다.

### 저장과 화면

`mesh/identity.sqlite3`를 v5로 갱신해 `mesh_runtime_profile` 한 행을 추가한다. 장치가 서명한 팀 ID·장치 ID·정확한 승인 이력·모드·네트워크 범위를 저장하며, 개인키나 Google·Firebase·Telegram·AI 토큰은 넣지 않는다. v1~v4의 기존 키·원본·발신 정책·수신 기록·사본·확인·충돌 기록은 유지한다. 마이그레이션 실패나 예상하지 않은 테이블은 기존 자료를 교체하지 않고 중단한다.

화면은 **이번 실행의 복구 허용**과 **다음 앱 시작의 자동 연결 동의**를 따로 표시한다. 현재 팀·남은 시간·일시 중지·네트워크 대기·재동의 필요 상태를 보여 주며, 연결이 꺼진 상태에서도 동의를 해제할 수 있다. 사용자가 선택 중인 다른 팀의 임시 문안은 복구 과정에서 지우지 않는다.

앱 설정의 일반 JSON이나 팀 공개 승인 자료만 복사해서는 자동 복구를 켤 수 없다. 다만 같은 Windows 사용자 환경의 전체 DB·키 백업 복원으로 과거 동의가 돌아오는 문제까지 해결하는 외부 단조 기록은 없다. 승인 이력의 기존 되돌리기 방지와 키 보관 한계는 유지한다. 이미 진행 중인 로컬 작업 스레드의 커밋까지 취소했다고 주장하지 않으며, 확인이 없으면 같은 원본을 재시도한다.

### 검증 범위

핵심은 `core/src/team/mesh/runtime/`와 `identity/consent.rs`, 네이티브 연결은 `src-tauri/src/mesh_lifecycle.rs`, `app.rs`, `main.rs`, `mesh_workbench.rs`다. 독립 진단 앱은 자동 복구·장치 키 저장소에 연결하지 않는다.

새 수명 테스트 17개는 자동 동의 없음, 앱 재실행, 절전과 중복 복귀, 예산 만료, 프로필 변경과 같은 범위의 DHCP, 승인 변경, 저장 동의 변조, 공용 네트워크 거부, 저장·해제 실패, 중지·종료와 시작의 경합, 실행 간격 감지, v4 보존을 확인했다. 이 테스트의 네트워크 프로필과 시간은 주입한 값이며, 키·SQLite·TCP 연결은 실제 구현을 사용한다.

별도로 이 PC의 실제 Wi-Fi에서 Windows 네트워크 프로필의 읽기·같은 주소 재탐색을 확인했다. 네이티브 테스트는 실제 전원 알림 등록·해제와 콜백 입력으로 동의 없는 연결이 열리지 않는 것을 확인했다. **컴퓨터를 실제로 절전시키거나 서로 다른 PC로 설치·UI를 시험한 결과는 아니다.** 기존 LAN 실험과 외부 보안 검토의 미완료 항목도 유지한다.

재연결 검사 중에는 수동 등록한 카드의 실행 ID가 광고와 같으면 상대의 최신 인증 등록을 생략할 수 있는 문제를 수정했다. 카드 등록과 새 도전으로 양쪽 확인을 마친 상태를 구분하며, 수동 등록 뒤 자동 발견만으로 양방향 기록 교환이 끝나는 회귀 테스트를 추가했다.

전체 워크스페이스 테스트 **190개**와 WebAssembly 검사·릴리스 화면 빌드가 통과했다. 전체 검사는 `--test-threads=4`로 실행해 실제 암호화·TCP 테스트의 동시 부하를 제한했다. 기본 실행에서 실제 LAN 지정 2개·OS 프로필 지정 1개·외부 Firebase 3개를 제외하며, OS 프로필 지정 검사는 별도로 통과했다. 전원 알림 테스트 1개와 재연결 회귀 테스트 1개는 기본 190개에 포함된다. UI 제어 ID·문서 링크·독립 진단 앱 분리도 확인했다.

다음 9절에서는 기존 공개 톡을 확인하고 선택한 내용만 관리자 PC에 별도 보관한다. 서버 DB 전체나 공용 비밀키를 임의의 팀원 PC로 복사하지 않는다.

## 9. 기존 공개 톡 확인과 이 PC 전용 보관

2026년 11월 16일, 기존 팀의 공개 톡을 **서버에서 새로 조회 → 사용자가 원문 선택 → 변경·삭제와 권한 재확인 → 이 PC에 보호해 보관**하는 경로를 추가했다. 기존 톡 화면의 서버를 전환하거나 과거 대화를 새 PC 팀원에게 재발송하는 기능은 아니다. 원본 서버가 닫혀 있으면 이 조회는 실패하며 화면 캐시로 대신 이전하지 않는다.

### 가져오는 범위와 권한

기존 화면의 톡·파일 캐시는 각각 최근 300개로 제한되며, 원본 삭제는 문서를 제거하는 방식이다. 따라서 캐시를 전체 이력이나 삭제 상태의 기준으로 사용하지 않는다. 기존 서버의 `teams/{team}/shares` 공개 컬렉션만 페이지별로 읽는다. 개인 문안, signals의 수신 범위, 연동 설정, 봇·API 키·토큰, 계정 백업, Drive 파일 본문을 조회하거나 복사하지 않는다.

대상 PC 팀에서는 현재 승인된 장치이며 운영 관리자 개인키를 가진 PC만 미리보기·보관을 수행할 수 있다. 원본 팀에서는 현재 로그인 계정의 member 문서와 admin 문서가 모두 있어야 한다. 원본 서버가 확인하는 관리자 역할에 의존하며, 화면의 과거 관리자 표시를 신뢰하지 않는다. 목록을 다 읽은 뒤 계정과 원본 관리자 권한을 다시 확인한다. 대상 PC 팀의 장치·정확한 승인 이력도 저장 직전에 SQLite 트랜잭션 안에서 다시 확인한다.

| 원본 공개 문서 | 처리 |
|---|---|
| 문서 ID와 `by`, `at`, `text`만 있는 유효한 공개 톡 | 미리보기 후보 |
| `url`이 있는 파일 항목 또는 파일 메타데이터 | 제외 |
| `aip-` ID 또는 기존 팀 약속 제안 접두어 | 연결된 제안의 의미를 잃지 않도록 제외 |
| 수신자·비밀키 등 추가 필드가 있는 문서 | 필드 내용은 보여 주지 않고 제외 개수만 표시 |
| 잘못된 작성 UID·시각·본문·길이 | 제외 |
| 다른 팀·컬렉션의 경로, 반복 ID·페이지, 손상된 응답 | 전체 조회 실패 |

이 필터는 문서 구조를 확인한다. 공개 톡의 자유 텍스트 안에 사람이 적은 비밀정보까지 판별하는 도구는 아니므로, 사용자가 본문을 확인하고 선택한다. 기존 작성 UID와 시각은 **원본 서버에 적혀 있던 값**으로 표시한다. 과거 작성자의 새 장치 서명이 있는 메시지로 가장하지 않는다. 기존 UID를 현재 PC 장치로 자동 매핑하지 않는다.

### 화면과 보관 흐름

설정의 **PC 팀 장치 등록 준비 → 내 장치와 관리자 승인 정보**에서 대상 PC 팀을 선택하고 **기존 팀 톡 확인·이 PC에 보관**을 펼친다.

1. 이 앱에 등록된 기존 팀을 선택해 **서버에서 새로 읽어 미리보기**를 누른다. 이때 보관 본문을 DB에 기록하지 않는다.
2. 원본 팀·대상 PC 팀·원문·작성 UID·기존 시각을 확인한다. 이미 같은 내용을 보관했거나 같은 원본 ID의 내용이 다른 항목은 표시하고 새 선택에서 제외한다.
3. 1~200개를 선택하고 **이 PC에만 보관하며 원본 수정·삭제는 자동 반영되지 않음**을 확인한 뒤 저장한다. 미리보기 유효 기간은 단조 시계로 5분이며 다른 조회가 이를 대체한다.
4. 네이티브 코드는 본문을 Webview에서 받지 않는다. 미리보기 토큰과 선택 ID만 받고 원본 목록을 다시 읽는다. 선택한 문서가 바뀌거나 사라졌거나 공개 톡 후보에서 제외되었으면 전체 선택을 보관하지 않는다.
5. 저장은 하나의 SQLite 트랜잭션으로 처리한다. 둘째 문서에서 오류가 나도 첫째 문서를 남기지 않는다. 같은 요청의 결과를 잃어 재시도하면 완료 결과를 돌려주며, 새 미리보기로 같은 원본·같은 내용을 선택해도 중복 삽입하지 않는다. 같은 ID의 다른 내용은 덮어쓰지 않는다.
6. 아래 보관 목록에서 이 PC의 사본을 50개씩 읽는다. 발송·편집·삭제 버튼은 제공하지 않는다.

팀이나 원본 선택이 바뀌면 UI의 이전 미리보기를 폐기한다. 늦게 도착한 응답으로 다른 팀에 저장하지 않으며, 네이티브에서도 정확한 서버 인스턴스·원본 팀·대상 팀·토큰·동의·선택 ID를 확인한다.

원본은 조회 사이에도 변경될 수 있다. 재확인 뒤 원본 서버와 로컬 커밋 사이에 발생한 수정·삭제까지 원자적으로 잠그지 않는다. 저장된 항목은 확인 시점의 별도 사본이며 이후 삭제가 전파되지 않는다는 점을 화면에 표시한다. 이를 전체 최신 이력이나 팀의 공식 전환 완료로 표시하지 않는다.

### 저장 형식과 한도

`mesh/identity.sqlite3`를 v6로 갱신해 `mesh_legacy_archive`를 추가한다. v1~v5의 키·승인 이력·톡 원본·발신 대기·수신·중계·확인·충돌 기록·자동 복구 동의는 유지한다. 예상하지 않은 기존 테이블이나 마이그레이션 실패는 자료를 자동 교체하지 않고 중단한다.

본문·원본 서버 식별자·원본 팀·작성 UID·원본 시각·조회 시각은 Windows 사용자 DPAPI로 보호한다. 보호 실패 시 평문으로 대신 저장하지 않는다. 보관 장치·대상 팀·승인 이력과 임의 salt를 포함한 본문 확인값에 대상 팀 관리자 키로 서명한다. 이는 **관리자가 이 사본을 확인해 보관했다는 서명**이며 과거 작성자 서명이 아니다. 읽을 때 장치·팀·과거 승인 이력·관리자 서명·본문 확인값을 모두 검증한다. 다른 장치 저장소로 같은 암호문을 옮겨 자기 보관 기록으로 읽을 수 없다.

원본 서버 범위·원본 팀·원본 ID의 해시로 중복을 구분한다. 서버 범위에는 서비스 종류·문서 서비스 주소·선택한 서버 ID를 쓰며 인증 토큰이나 공용 키를 쓰지 않는다. 원본 서버 주소나 서버 ID가 바뀐 경우 자동으로 같은 원본이라 판단하지 않는다. 서버 복제본 간 중복 정리는 후속 정책이 필요하다.

| 한도 | 값 |
|---|---|
| 원본 조회 | 공개 문서 1,000개, 디코딩한 합계 4 MiB, 페이지 최대 16개 |
| 원본 HTTP 응답 한 번 | 2 MiB, Content-Length와 실제 수신량 모두 검사 |
| 페이지 요청 | 100개씩, 반복 토큰 거부 |
| 한 번의 새 조회 제한 시간 | 45초, 캐시 대체 없음 |
| 한 번의 보관 선택 | 200개 |
| 대상 PC 팀별 보관 | 1,024개, 목록 한 페이지 50개 |

보관은 `mesh_local_events`·발신 정책·outbox·courier·수신 확인 테이블에 기록하지 않는다. LAN 연결이나 대표 PC가 켜져 있어도 이 과거 사본은 자동 전송되지 않는다. 원본 서버의 문서·계정·연동 설정도 변경하지 않는다. 같은 Windows 계정 전체 백업과 관리자 개인키 보호의 기존 한계는 유지한다.

### 검증과 남은 단계

새 테스트 22개는 화면 캐시 300개를 넘는 새 조회, 공개 스키마 제외, 선택한 원본 변경·삭제, 두 관리자 권한, 대상 승인 변경, 토큰·동의·만료·서버 일치, 중복·충돌, 트랜잭션 전체 롤백, 헤더·암호문 변조, 다른 장치의 사본 거부, 페이지와 v5 보존을 확인한다. 실제 루프백 HTTP 서버로 페이지 토큰 인코딩, GET·허용 경로만 사용, 권한 재확인, 다른 문서 경로·반복·손상 응답과 개수·바이트·페이지 한도도 검사한다. 외부 운영 서버의 실데이터를 수정하지 않고 메모리 원본·로컬 HTTP 모형과 실제 SQLite·DPAPI·서명을 사용한다.

이번 단계의 전체 워크스페이스 검사는 `cargo test --locked --workspace --target x86_64-pc-windows-msvc --features sai/connection-test -- --quiet --test-threads=4`로 **212개 통과·6개 제외**했다. 제외한 것은 기존의 실제 LAN 지정 2개·OS 프로필 지정 1개·외부 Firebase 3개다. Windows 네이티브 검사와 WebAssembly 검사, 릴리스 화면 빌드도 통과했다. 새 화면 제어 14개의 HTML 연결·ID 중복·문서 링크·진단 앱 분리와 새 모듈의 형식 검사를 확인했다. 실제 GUI를 조작한 검증 결과는 아니다.

기존 톡의 원본 UID와 승인 장치의 연결, 과거 내용의 공유 범위, 기존 서버의 삭제 상태, 원본 쓰기 중단과 전환 시점, 복구 가능한 전체 이전은 남아 있다. 아래 10절에서 새 PC 톡을 실제 대화 화면에 연결하고 PC 톡 자체의 삭제 요청을 구현했다. 기존 서버 톡은 별도 경로로 유지한다. 실제 두 PC 설치·절전·배포 UI와 운영 서버 접속 확인도 완료한 것으로 간주하지 않는다.

## 10. 대화 화면의 PC 톡과 작성 장치의 삭제 요청

Drive 탭에 **기존 서버 톡 / 파일 공유 / PC 톡**을 나란히 제공한다. PC 톡의 팀 선택·조회·새 작성·삭제 요청은 PC 승인 저장소만 사용한다. Firebase 로그인이나 기존 팀 참여, Google 로그인, 기존 서버 응답을 새 PC 톡 API의 조건으로 요구하지 않는다. 기존 서버의 톡·파일 경로와 9절의 로컬 보관 사본을 이 대화방에 자동 합치지 않는다.

### 사용과 작성자 표시

1. 관리자가 승인한 PC 팀의 장치 정보를 먼저 등록한다. 설정에 있던 장치·연결 기능을 그대로 사용한다.
2. **Drive → PC 톡**을 열고 PC 팀·승인 이력·내 장치와 대상 장치 수·ID를 확인한다. 기존 서버의 상단 팀 선택과 PC 톡의 팀 선택은 별개다.
3. 표시한 승인 장치에 전달하는 것을 선택한 뒤 1~1,000자의 톡을 저장한다. 연결이 꺼져 있어도 SQLite의 원본·발신 정책·대기를 한 트랜잭션으로 저장한다. 연결 시작은 이 체크박스로 실행하지 않는다.
4. 설정에서 해당 PC 팀의 기록 교환·LAN 자동 연결을 시작하면 기존 상호 TLS·HPKE·서명·중계 경로로 전달한다. 15분 예산과 별도 자동 복구 동의의 범위는 유지한다.
5. 화면은 이 PC 저장, 상대 저장 확인 대기, 대상 PC 저장 확인, 승인 변경으로 전달 보류와 충돌을 구분한다. 저장 확인은 메시지를 읽었다는 뜻이 아니다. 목록은 50개씩 조회한다.

작성자는 이벤트 서명으로 확인한 **장치 ID**로 표시한다. 원본의 작성 장치와 관리자 승인 이력의 구성원 ID를 대조하며, 전체 장치·구성원·이벤트 ID는 메시지의 보조 정보로 제공한다. 과거 Firebase UID를 현재 사람이나 장치에 자동 연결하지 않는다. 기존 준비 기록도 별도 표시하며 작성 시각을 만들어 붙이지 않는다. v2 PC 톡의 시각은 작성 PC가 서명한 값으로 화면 정렬에만 쓰고 권한·삭제 우선순위의 기준으로 삼지 않는다. 같은 시각은 장치 ID·순번으로 정렬한다.

새 작성과 삭제 요청에는 조회한 팀·장치·승인 revision·membership head를 함께 전달한다. 트랜잭션 안에서 현재 승인과 정확히 같아야 한다. 승인 범위가 바뀌면 체크박스를 해제하고 임시 문안은 보존한다. 요청 ID로 재시도하며, 이미 저장된 같은 본문은 작성 시각이나 메시지 ID를 새로 만들지 않는다. 다른 팀을 보고 있을 때 도착한 응답으로 그 팀의 목록이나 문안을 바꾸지 않는다. 문안은 현재 앱 실행의 팀별 메모리에 보관하며 영구 임시 문안 저장 기능은 아니다.

### 삭제 요청의 의미와 검증

PC 톡은 **원본을 작성한 같은 장치**에서만 삭제 요청할 수 있다. 운영 관리자도 다른 장치가 쓴 톡을 삭제하는 권한을 자동으로 얻지 않는다. 현재 승인된 장치여야 하며, 다른 장치·팀·잘못된 순번·준비 기록이나 삭제 요청 자체를 대상으로 한 요청은 거부한다. 같은 요청 ID는 재사용하고 이미 삭제한 항목에 새 삭제 요청을 만들지 않는다.

삭제는 원본 로그 행을 제거하지 않고, 원본보다 높은 작성 장치 순번에 새 서명 이벤트를 추가한다. 서명 헤더의 `retract`에는 **원본 이벤트 ID와 그 장치 순번**만 담는다. 자유 텍스트나 JSON처럼 보이는 메시지를 삭제 명령으로 해석하지 않는다. 새 본문의 버전·작업 종류·시각·salt·텍스트는 별도 용도의 확인값에 묶고, 헤더와 본문의 삭제 대상도 일치해야 한다.

목록을 만들 때 전체 검증 이력의 삭제 요청을 먼저 적용한 뒤 페이지를 고른다. 원본이 같은 작성 장치에서 왔고, 정확한 ID·순번이 일치하며, 더 낮은 순번과 같거나 과거 승인 이력에 있을 때만 숨긴다. 다른 작성자가 유효한 자기 서명으로 같은 대상 ID를 지목해도 원문을 숨기지 않는다. 삭제한 자리는 안내로 남고 본문은 반환하지 않는다. 설정의 준비 기록 목록에도 같은 숨김을 적용한다.

승인이 바뀌어 과거 본문을 보낼 수 없는 경우에도 서명된 삭제 참조는 헤더로 전달한다. 이미 원문을 가진 PC는 이를 검증해 숨기며, 새 팀원에게 과거 본문을 재암호화하지 않는다. 과거 승인 범위에서 만든 삭제 요청도 새 승인 연결에서 헤더만 다시 전달하고 확인받을 수 있다. 새 구성원은 원본과 삭제의 식별자를 알 수 있지만 과거 본문을 받지 않는다.

삭제 참조가 디스크에 저장됐다는 수신 장치의 서명 확인은 `reference-stored`로 구분한다. 본문 없는 일반 톡의 확인을 본문 전달 완료로 바꾸지 않는다. 암호문 중계 보관 응답도 최종 수신자의 저장 확인을 대신하지 않는다. 상대의 서명 확인을 받지 못하면 발신 대기·보류 상태를 유지한다.

이것은 앱 화면에 반영되는 삭제 요청이다. 로컬 DPAPI 원본·수신 암호문·중계 사본·백업을 물리적으로 지우거나, 이미 읽고 복사한 내용을 회수하지 않는다. 상대가 오프라인이면 연결 뒤 검증한 시점부터 반영된다. 같은 원본의 암호문을 다시 받아도 삭제 요청이 남아 있는 저장소에서는 본문이 다시 표시되지 않는다. 모든 사본을 삭제 전의 백업으로 함께 되돌리거나 외부에 저장한 복사본까지 막는 외부 단조 기록은 없다.

### 형식과 호환성

SQLite 테이블은 v6를 유지하고 기존 행을 다시 쓰지 않는다. 새 PC 톡과 삭제 작업은 원본 헤더·본문의 v2 형식을 사용한다. v1 준비 원본의 해시·서명·본문 직렬화는 유지한다. 키·승인·발신·수신·중계·동의·로컬 보관 사본을 초기화하지 않는다. 기존 한도인 작성 장치별 원본 1,024개, 팀 수신 원본 1,024개에 삭제 이벤트도 포함된다. 한도에 도달한 뒤의 보관·압축·삭제 전용 예산은 후속 운영 정책이 필요하며 무제한 운영 버전으로 표시하지 않는다.

기록 교환 연결 정보에 `record_version: 2`를 추가하고 해당 값을 장치 서명의 연결 확인값에 묶는다. 값을 지우거나 바꿔 기능을 낮추는 카드는 검증에 실패한다. 서명은 맞아도 과거 기록 교환 버전이면 업데이트 안내로 거부한다. **기록 교환할 PC는 모두 이번 앱 형식을 사용해야 하며**, 이전 연결 카드를 다시 사용하는 방식으로 호환을 우회하지 않는다. 독립 연결 진단의 확인 모드는 이 기능의 저장소·계정·새 IPC에 접근하지 않는다.

### 검증과 남은 범위

추가 테스트 15개는 작성 장치와 저장 확인, 재시도·시각 유지, 승인 범위 변경, 작성 장치 외 삭제 차단, 원문 재전송 뒤 숨김 유지, 과거 본문의 재배포 없는 헤더 삭제, 승인 변경 뒤 과거 원문의 삭제, 저장 실패 롤백, 페이지 밖 삭제 적용, 강퇴 장치의 읽기와 쓰기 거부, v1 직렬화와 v2 메타데이터 변조, 다른 작성자의 유효 서명으로 삭제 시도, 실제 루프백 상호 TLS 재연결, 서명된 형식 협상과 과거 앱 거부, 작성 PC가 빠진 중계·최종 확인을 검사한다.

전체 워크스페이스 테스트는 앞 절과 같은 Windows x64 명령으로 **227개 통과·6개 제외**했다. 마지막 쓰기 한도 표시 보완 뒤 PC 톡 테스트 12개를 다시 통과했다. Windows 네이티브 검사, WebAssembly 검사와 최종 릴리스 화면 빌드도 통과했다. PC 톡 제어 12개의 HTML 연결·ID 중복·태그 균형·문서 링크·진단 앱 분리·chat 창 IPC 제한과 수정한 모듈의 형식 검사를 확인했다. 네트워크 검증은 한 PC에서 서로 다른 키·저장소·실제 TCP·상호 TLS·DPAPI·HPKE로 수행했으며, 실제 여러 PC의 UI를 조작한 결과는 아니다.

새 PC 톡의 일반 화면 경로를 연결했으며, 기존 서버 대화를 이 방으로 완전히 이전한 결과는 아니다. 기존 UID와 사람이 확인한 장치의 연결, 과거 보관 사본의 재공유 승인, 기존 서버 쓰기 중단·삭제 상태·전체 이전과 복구, 여러 PC 설치·UI·실제 절전, 원격 네트워크 연결과 외부 보안 검토는 남아 있다. 두 번째 PC 실험을 지금 마쳐야 다음 개발을 진행할 수 있는 조건으로 삼지 않는다.
