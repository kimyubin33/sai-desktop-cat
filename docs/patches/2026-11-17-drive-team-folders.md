# 2단계 세 번째 패치 — Drive 팀 폴더 만들기·초대·복원

2026-11-17. [개발 계획](../development-direction.md)의 팀 연결 실행 경로를 구현했다. **실제 Google 계정의 동의·공유·다른 PC 검증은 남아 있다.** 정식 릴리스와 버전 변경은 하지 않으며 v0.9.14 작업본이다.

## 사용자 흐름

1. Google 로그인으로 이름·기본 설정·기억한 팀 목록을 읽는다.
2. 파일 화면의 **팀 Drive 연결**을 누를 때 앱이 만들거나 사용자가 선택한 Drive 자료의 접근 권한을 요청한다. 서버 주소·폴더 ID·개발용 JSON은 입력하지 않는다.
3. **팀 만들기**에서 이름을 입력하면 내 Drive에 사이 팀 폴더를 만든다. 공개 링크 권한은 만들지 않는다.
4. 폴더 소유자는 **팀 관리**에서 팀원의 Google 이메일을 입력하고 **초대 보내기**를 누른다. 해당 계정에 편집 권한을 추가하며 Google 알림 메일 발송을 요청한다. 기존 편집자에게는 다시 메일을 요청하지 않는다. 기존 보기 권한은 명시적인 초대 동작으로 편집 권한으로 올린다. 메일 배달 자체까지 확인했다고 표시하지 않는다.
5. 초대받은 팀원은 앱의 **초대받은 팀 연결**을 누르고 시스템 브라우저의 Google 선택창에서 사이 팀 폴더 하나를 선택한다. 앱과 같은 계정을 사용해야 한다. 링크를 붙여 넣거나 연결 정보를 교환하지 않는다.
6. **폴더 열기**는 접근 권한을 다시 확인한 뒤 Google Drive를 연다. 이번 파일 업로드·다운로드는 Drive 화면에서 이용한다. 앱 안의 파일 목록·선택·업로드는 3단계에서 구현한다.
7. 기억한 팀 참조는 기존 개인 설정 변경 기록에 합쳐 동기화한다. 새 PC에서 복원한 참조는 미확인 상태로 시작하고, 현재 Google 권한을 확인해야 열린다.

**내 목록에서 빼기**는 계정의 기억한 참조만 제거한다. 팀 폴더·파일을 삭제하거나 Google 공유 권한을 취소하지 않는다. UI에서도 이 차이를 안내한다. 탈퇴·권한 취소를 구현한 것으로 간주하지 않는다.

## 인증과 권한

기본 로그인은 `openid`, `email`, `drive.appdata`를 유지한다. 팀 Drive 연결에서 같은 세 범위와 `drive.file`을 함께 요청하고, 검증된 기존 subject와 다른 계정을 선택하면 기존 연결을 보존하며 거절한다. 전체 `drive`, `drive.readonly`, Calendar·Tasks 범위는 새로 요청하지 않는다. 과거에 더 넓은 범위를 받았던 Google 권한까지 취소했다고 주장하지 않는다.

2026-10-12 갱신된 [Google 데스크톱 Picker 안내](https://developers.google.com/workspace/drive/picker/guides/desktop-mobile-picker)를 확인했다. 이 선택 흐름은 `drive.file` 하나만 허용하므로 기본 OIDC·appData 로그인과 분리한다. 시스템 브라우저에서 `trigger_onepick=true`와 폴더 선택 옵션을 사용하고, 기존 루프백·PKCE·state 보호와 취소를 적용한다. WebView 안에 Google 인증·Picker를 넣지 않는다. 사용자가 취소하면 기존 계정과 팀 목록을 바꾸지 않는다.

Picker 전용 응답은 OIDC 신원이 아니다. 확인된 앱 계정 토큰과 Picker 토큰 각각으로 고정된 Google Drive `about.get`을 요청해 Google이 반환한 `user.permissionId`가 같은지 대조한다. 표시 이메일이나 프런트엔드 입력을 신원의 근거로 쓰지 않는다. 일치한 Picker의 Drive 전용 refresh token만 기존 subject에 연결해 DPAPI로 보호한다. 원래 OIDC·appData refresh token과 subject는 교체하지 않는다. 이후 Drive 전용 갱신에서도 같은 permission ID인지 확인한다. [Drive 사용자 필드](https://developers.google.com/workspace/drive/api/reference/rest/v3/User), [about.get의 허용 범위](https://developers.google.com/workspace/drive/api/reference/rest/v3/about/get)를 근거로 사용한다.

선택창이 반환한 폴더 ID만으로 참여하지 않는다. 현재 계정에 묶어 검증한 토큰으로 Drive 메타데이터를 다시 읽고 폴더 형식·삭제 상태·사이 팀 표시·목록 접근 능력을 확인한다. 팀 만들기에는 앱 표시와 생성 작업 ID를 기록하지만, 이 표시는 접근 권한의 근거가 아니다. 폴더 소유자이며 현재 `canShare`가 참인 경우만 앱에서 초대한다. 새 공유 권한은 입력한 `user` 대상의 `writer`로만 생성한다. `anyone`·도메인 전체·소유권 이전은 새 경로에서 사용하지 않는다. 소유자가 Drive에서 별도로 변경한 공유 설정은 Google 권한을 따른다.

인증·선택·파일 요청·로컬 반영은 계정 연결 세대에 묶인다. 다른 계정의 늦은 응답을 현재 계정에 반영하지 않는다. 각 열기·초대 동작에서도 다시 접근을 확인하므로 이전 목록의 확인 표시가 권한 취소를 우회하지 않는다. 오프라인·할당량 오류가 발생하면 나머지 팀마다 같은 요청을 반복하지 않고 확인 불가로 표시한다.

## 응답 유실과 팀 참조 보존

- 팀 폴더 생성 작업을 로컬 계정 사본에 먼저 보관한다. 사전 발급한 Drive 파일 ID도 생성 요청 전에 커밋한다.
- 생성 후 응답이 끊겨도 **이어 만들기**에서 같은 ID·작업 표시를 대조한다. 같은 이름을 검색해서 다른 사람의 폴더를 선택하거나 새 폴더를 계속 만들지 않는다. 저장 결과가 다른 자료라면 덮어쓰지 않는다.
- 폴더 확인과 팀 참조 기록을 마친 뒤 로컬 생성 대기를 해제한다. 앱 재시작 후에도 미완료 작업을 다시 확인할 수 있다.
- 초대 전에는 현재 공유 권한 목록의 모든 페이지를 확인한다. 응답 유실 후 재시도에서도 기존 편집 권한을 먼저 확인한다. 권한 생성·갱신 뒤에는 편집 권한을 다시 확인해야 결과를 표시한다. 외부에서 동시에 권한을 바꾸는 상황의 최종 상태는 Google이 판단하며, 앱이 원격 작업 전체의 exactly-once 실행을 보장하지는 않는다.
- 목록에서 빼는 변경은 기존 참조 병합 규칙의 삭제 기록으로 동기화한다. 참조를 빼도 원본 폴더·파일·공유 권한은 유지한다. 이전 Firebase 팀을 자동 업로드하지 않는다.

## 검증

자동 검사 전체 **100개 통과**, 기존 Firebase 실서비스 검사 3개는 실행 제외했다. Wasm UI·x64 Windows 빌드를 확인했다. 이번에 추가한 11개 자동 검사는 모의 Google HTTP·루프백 응답을 사용한다.

실제 자료와 분리한 네이티브 미리보기에서 로그인 전 파일 화면의 팀 영역과 안내 문구를 확인했다. 로그인 전에는 팀 생성·초대·폴더 열기 버튼을 노출하지 않는다. 초대 이메일 초안 보존과 늦은 목록 응답 무시는 UI 상태 처리에 추가했다. 로그인 후 카드와 실제 초대 화면을 실계정으로 검증한 것은 아니다.

- 폴더 생성 후 오류 응답 → 앱 재시작 → 동일 ID 재확인에서 실제 생성 1회와 참조 1개 유지.
- 팀 참조를 다른 로컬 설치로 복원 → 현재 접근 확인 → 공유 해제에 해당하는 404 응답 후 열기·초대 거절.
- 참조 삭제 동기화 후에도 Drive 원본 폴더 유지.
- 편집 가능한 비소유자 초대 거절, 명시한 계정만 편집자로 추가, 응답 유실 후 중복 초대 요청 방지, 보기 권한의 명시적 갱신.
- 일반 폴더·문서·경로 문자열·기억하지 않은 폴더·이전 계정 세대·Drive 권한 없는 기본 로그인 거절.
- 기본 로그인·Drive 연결·Picker의 서로 다른 scope 집합 확인, Picker 응답의 단일 ID 제한, 루프백 선택 완료와 토큰 비노출.
- 다른 Google subject 또는 다른 Drive permission ID 선택 시 기존 계정·자격 증명 보존. Drive 전용 토큰의 재시작·갱신·계정 불일치 거절 및 OIDC 계정 유지.

**실계정 Google 로그인, 메일 배달, 실제 두 계정·두 PC, 다른 계정의 신규 하위 파일 접근, 조직 정책·Google 공유 드라이브는 검증 완료가 아니다.** 현재 생성 대상은 개인 My Drive 안의 팀 폴더이며 조직의 Shared Drive 생성을 지원하지 않는다. 최대 연결 팀 수는 32개이고 개인 변경 기록 한도·조회 비용 제한은 이전 패치와 같다. 3단계의 파일 공유를 구현하기 전에 `drive.file`에서 선택 폴더와 다른 사용자가 추가한 하위 파일의 접근 범위를 실계정으로 확인해야 한다. 범위가 부족하다고 전체 Drive 권한으로 조용히 확대하지 않는다.

운영자는 배포용 Google 프로젝트에서 Drive API·Google Picker API 활성화, OAuth 클라이언트 종류·공개 상태·테스트 사용자·동의 범위를 확인한다. 이는 앱 운영자의 준비이며 일반 사용자에게 콘솔 설정을 요구하지 않는다. 이 패치는 Google 콘솔 상태를 변경하지 않았다.

다음 단계는 **앱 안의 팀 파일 목록·선택·업로드·다운로드**다. 2단계 완료 표시는 실계정·권한 거절·공유 취소·새 PC 복원 검증까지 마친 뒤 한다.
