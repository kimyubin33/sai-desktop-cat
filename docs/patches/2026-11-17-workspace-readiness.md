# 전체 흐름과 검증 빌드 점검 — 2026-11-17

설치·실사용 검증에 앞서 **저장된 Google 연결 → 팀 복원 → 파일 → AI 업무 검토 → 내 Calendar**의 연결을 로컬에서 점검했다. 시작 시 화면 복구와 설정 입력 보존을 수정하고, 검증용 빌드 절차를 현재 Google 제품 방향에 맞췄다. 실제 OAuth 승인·실계정 파일/일정 변경 시험·유료 AI 호출·서비스 배포·정식 릴리스는 하지 않았다.

## 화면에서 바뀐 동작

- 앱 시작 전에 계정 재확인이 끝난 경우에도 계정 표시와 팀 목록을 함께 불러온다. 첫 재확인이 일시적으로 실패한 뒤 백그라운드에서 성공하면 연결 성공 안내로 갱신한다. 이전 실패 안내만 남아 다시 로그인하게 만드는 혼동을 줄였다.
- 계정·팀 상태를 겹쳐 읽어도 늦게 돌아온 이전 응답이 최신 화면을 덮지 못하게 한다. 계정 전환·로그아웃의 기존 세대 검사도 유지한다.
- 자동 동기화가 일어나도 입력 중인 기기 설정·개인 AI 모델·새 키 입력을 지우지 않는다. 저장 성공 후 최신 값을 표시하며 실패하면 초안을 유지한다. 저장된 개인 키의 명시적 제거는 해당 입력만 비우고 다른 초안을 유지한다.
- 파일 화면 전환이 진행 중이거나 계정 상태가 달라 거부될 때, 협업의 선택 팀만 따로 바뀌지 않게 했다.

## 모의 PC 두 개의 통합 검사

Google 기능의 외부 진입점과 실제 파일 저장소를 사용하되 Google·Claude 응답은 루프백 모의 서버가 제공한다. PC A/B는 별도 설정·Google 저장 폴더를 사용하고 각각 가짜 OAuth 교환으로 연결한다. 이전 PC의 토큰을 복사해서 복원을 통과시키지 않는다. 옛 팀 서버나 브라우저 열기 경로를 호출하면 검사가 실패한다.

| 검사 | 확인한 결과 |
|---|---|
| A에서 이름·설정·팀 저장 후 B에서 같은 계정 연결 | B가 복원하며 빈 기본값을 원격에 업로드하지 않음 |
| 파일 업로드 → 본문 확인 → Claude 후보 검토 → 업무 저장 → Calendar 추가 | B에서 파일 바이트·업무·같은 일정 복원. AI 재호출과 일정 중복 없음 |
| B에서 일정 수정 후 A의 오래된 삭제 검토 실행 | 변경 충돌로 중단하며 B의 변경 보존 |
| 앱 종료 후 같은 저장소로 다시 시작 | 보호된 연결·이름·팀 복원, 브라우저 재인증·기본값 업로드 없음 |
| 최초 원격 설정 복원 실패 후 재시도 | 빈 팀 목록으로 원격을 덮거나 파일 쓰기를 열지 않고, 회복 후 기존 정보 복원 |
| 로그아웃·다른 계정 전환 | 이전 계정의 팀·대기 자료를 숨기며 원격 파일 보존 |

모의 Drive는 개인 앱 공간과 일반 팀 파일을 구분해 목록을 반환한다. 접근 오류 시 파일 API는 빈 목록과 오류 상태를 반환하는 기존 계약을 검사하며, 빈 목록을 정상 접근으로 간주하지 않는다. 실제 Google 동작·네트워크·설치 환경을 재현한 검사는 아니다.

## 빌드와 배포 절차

1. PR·`main` 소스 변경은 `check-workspace.yml`에서 Wasm·Rust·AI 중계·빌드 설정 검사를 실행한다. Google 로그인 정보나 Claude 키 없이 검사한다.
2. `build-windows.yml`은 전환 중 **수동 검증 빌드**로 실행한다. 개발 측 `GOOGLE_CLIENT_JSON`을 검증하고 포함한다. 누락·잘못된 데스크톱 앱 형식이면 설치 파일을 만들지 않는다. 형식 검사에 연결 정보·예외 원문을 출력하지 않는다. 일반 사용자에게 JSON 입력을 요구하지 않는다.
3. 검사·NSIS 빌드·실행 파일 CPU 확인이 통과하면 x64/ARM64별 `Sai-Preview-Setup-*`, `Sai-Preview-Portable-*`, 체크섬만 Actions 아티팩트로 모은다. 옛 팀 서버 ZIP과 PC 톡 사용 안내는 제외한다.
4. 이 워크플로는 Releases·자동 업데이트 메타데이터를 발행하지 않는다. 버전 번호를 올려 푸시하는 것만으로 전환 중 제품을 정식 배포하지 않는다. 기존 릴리스와 역사 자료는 보존한다.

이 변경으로 GitHub 워크플로를 실행하거나 설치 파일을 만들지는 않았다. OAuth 형식 검사는 Google 등록·동의 화면 공개 상태·API 활성화를 확인하는 검사가 아니다. Claude 공개 원점은 개발 측 빌드 변수로 제공하며, 미설정 빌드는 준비 중으로 표시한다. 실제 비용·키·배포는 [운영 계약](../../services/team-ai/README.md)의 별도 단계다.

## 로컬 검증 결과

- `cargo test --locked --workspace --target x86_64-pc-windows-msvc -- --test-threads=4`: **202개 통과** — core 196, native 4, UI 2. 기존 Firebase 실계정 검사 3개는 제외 상태다.
- `node --test services/team-ai/gateway.test.mjs scripts/check-google-client.test.mjs`: **20개 통과** — 중계 17, 빌드 설정 3. 전체 **222개 통과**다. 이번에 모의 통합 검사 4개와 빌드 설정 검사 3개를 추가했다.
- Wasm 화면 빌드와 Windows x64 개발 빌드 통과. 로컬 Google 연결 파일은 내용 출력 없이 형식만 확인했다. 최신 네이티브 앱은 별도 미리보기 자료 폴더로 실행을 확인했으며 실계정 수용 시험으로 집계하지 않았다.
- 자격 증명 없는 가상 화면에서 첫 재확인 실패 후 팀 자동 복구·연결 성공 안내, 주기적 프로필 갱신 중 모델 입력 보존, 명시적 설정 저장을 확인했다. 실제 인증·권한 창은 조작하지 않았다.
- 변경 파일의 공백 오류와 빌드 워크플로의 PowerShell 구문을 확인했다. GitHub Actions 자체 실행·NSIS 설치·ARM64 빌드는 확인하지 않았다.

## 다음 실사용 검증 순서

별도 연결 진단 ZIP이나 PC 서버 설정은 사용하지 않는다. 운영 측 Google 등록·동의/테스트 사용자·Drive/Calendar API 준비를 확인한 검증 설치 파일로 다음을 시험하고 결과를 기록한다. 실제 계정의 로그인·권한 동의는 사용자가 직접 한다.

| 순서 | 동작 | 통과 기준 |
|---|---|---|
| 1 | PC A에서 설치·Google 로그인·팀 생성·이름 저장 | 사용자용 서버·JSON 설정 없이 진행, 정상 파일 작업에서 반복 로그인 없음 |
| 2 | 초기 상태 PC B에서 같은 Google 계정 로그인 | 이름·설정·참여 팀 복원, A의 원격 정보 보존 |
| 3 | 다른 계정 팀원 초대 후 파일·협업 교환 | PC/Drive 사본 추가와 다운로드 내용 일치, 충돌 시 양쪽 내용 보존, 소유자 PC를 꺼도 접근 가능 |
| 4 | 각자 Calendar 연결·추가·수정·삭제 | 본인 일정만 변경, 같은 업무는 한 개, 동시 변경 거부, 팀 업무·파일 보존 |
| 5 | 인터넷 단절·앱 재시작·로그아웃·계정 전환·공유 해제 | 잘못된 성공 표시·계정 간 자료 노출·원격 덮어쓰기·자동 중복 전송 없음 |
| 6 | 비용·운영 설정을 마친 Claude 중계에서 명시적 분석 | 선택한 본문만 전송, 팀 권한·한도 준수, 검토한 업무만 저장, 공용 키 비노출 |
| 7 | 실제 Windows x64/ARM64 설치·업데이트·기존 자료 보존 확인 | 결과와 미지원 범위를 기록한 뒤 정식 배포 여부 판단 |

자동 등록·다른 캘린더 선택·시간 지정 일정은 이번 수용 범위에 넣지 않는다. 실사용 증거가 없는 항목은 완료로 표시하지 않는다. 팀 AI가 미배포인 동안에도 로그인·파일·협업·Calendar의 실제 검증은 진행할 수 있다.
